# HWP/HWPX → PDF 변환 방식 비교 (2026-10-16)

비교 대상
- **한/글 COM**: 앱이 쓰는 방식. 한/글(이 PC는 한컴오피스 NEO)로 문서를 열어 `SaveAs(…, "PDF")`
- **rhwp CLI**(rhwp v0.8.7, MIT, github.com/edwardkim/rhwp, 공개 배포 Windows 실행 파일·SHA-256 확인): `export-pdf --backend svg`(기본)·`--backend direct`
  - 한/글 없이 혼자 PDF를 만드는 방식이다(브라우저용 HWP 뷰어들이 쓰는 rhwp 렌더러와 같은 엔진).

측정 방법: 같은 PC, 111 폴더 실제 문서 사본 7개(HWPX 5·HWP 2, 2~36쪽), 각 방식 1회. 한/글 결과를 기준으로
쪽 수, 글자 일치도(추출 글자 순서 비교), 그림 차이(쪽마다 회색조 평균 픽셀 차, 앞 6쪽)를 봤다.

- rhwp svg는 한/글보다 3.6배 느리고 글자 일치도도 0.49~0.92로 낮다.
- rhwp direct는 성공한 문서에서 2~5배 빠르지만,
  - 7개 중 2개를 그라데이션 채우기 때문에 변환하지 못했고(공문서 표지·강조 상자에 흔함),
  - 1개는 쪽 수가 달라졌고(35→36쪽),
  - 그림 비교에서 일부 굵은 글씨(예: '(개요)' 라벨)와 병합 칸 오른쪽 테두리가 빠졌다.
- 한/글 전용 글꼴 폴더(`Shared\TTF\Hwp`·`All`)를 `--font-path`로 넘겨도 일치도·그림 차이가 거의 같았다
  (차이는 글꼴보다 조판·그리기 단계에서 생긴다).

## 결정

**한/글 COM 방식을 그대로 쓴다.** 앱은 한/글이 필수 환경이라 추가 설치가 없고, 결과가 한/글 화면·인쇄와
쪽 구성·글꼴·굵기·테두리까지 같다. 공문서 PDF는 원본과 같아야 하므로 속도보다 정확성을 우선했다.
rhwp CLI(실행 파일 약 49MB)는 실패·쪽 어긋남이 있어 대체 경로로 동봉하지 않는다. 한/글 경로는 이미
'열기 → PDF 저장' 두 단계만 하므로 앱 쪽에서 더 줄일 시간은 없다(대부분 한/글 내부 PDF 생성 시간).

rhwp는 대신 서식 미리보기(설정·서식 요소 편집의 한/글 조판 미리보기, WASM)에 쓴다.
rhwp가 그라데이션을 지원하고 쪽 나눔이 한/글과 같아지면(새 버전) 같은 방식으로 다시 측정한다.
