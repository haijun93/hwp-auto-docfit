# Beta 12 코드 리뷰 및 PAX 벤치마킹 재평가

기준일: 2026-10-09(KST). 대상: **v1.72 Beta 12**, `main`의 `03fdccc44b3b54b0d0ea224e85953eea23f685b1`. 앞선 PAX 조사 기준 `0cb80f7`(1.73 Alpha 1)과 구별한다.

## 1. 먼저 해결할 리뷰 발견

우선순위는 P1(사용자 처리·배포·품질 판정에 영향), P2(검증·운영 보강)다. 아래는 수정 제안이며 이번 작업에서는 제품 코드를 변경하지 않았다. 재현 결과는 [JSON](benchmarks/Beta12_리뷰_재현결과_2026-10-09.json)에 보관했다.

### R1 · P1 · 업데이트가 부모/자식 PID 두 개를 기다리지 못함

- 위치: `hwp-auto-docfit.py:18123`, `docfit_core/updater.py:45`, `docfit_core/updater.py:55`.
- 앱은 `powershell.exe -File … -WaitPids "자식PID,부모PID"` 형식으로 전달한다. 스크립트 매개변수는 `[int[]]$WaitPids`다.
- 같은 Windows PowerShell 호출 방식으로 안전한 매개변수 출력 스크립트에 `123,456`을 전달한 결과 **`count=1, values=[123456]`**이었다. 배열 두 개가 아니라 쉼표를 포함한 숫자 하나로 바인딩된다.
- 따라서 실제 PyInstaller 프로세스 두 개를 기다리지 못하고, 존재하지 않는 PID 대기 오류는 `SilentlyContinue`로 무시한 채 교체에 들어갈 수 있다. 파일 잠금·복사 실패·재시도 위험이 남는다. 실제 EXE 교체 실패까지 이번에 재현한 것은 아니다.
- 제안: PID 목록을 문자열/JSON으로 전달하고 스크립트에서 명시적으로 분해·정수 검증하거나, 자식/부모 PID를 각각의 매개변수로 전달한다. 대기 시간 초과는 교체 중단 상태로 처리한다.
- 필요한 시험: **Python subprocess→실제 PowerShell 매개변수 바인딩** 통합 시험. 현재 `tests/test_updater.py`는 스크립트 문자열 존재/순서 검사라 이 문제를 잡지 못한다.

### R2 · P1 · 부분 편집 실패 때 문단 글 캐시가 실제 내용과 달라짐

- 위치: `hwp-auto-docfit.py:13826`(쉼표 보정), `13926`(연속 공백 보정), `14219`(규칙 결과), `14324`(캐시 읽기).
- 캐시는 규칙 반환값이 0보다 클 때만 비운다. 하지만 보정 함수는 **삭제→삽입→수정수 증가** 순서로 동작하고, 중간 실패는 로그를 남긴 뒤 계속한다.
- 실제 Beta 12 함수 본문을 AST로 추출하여, 삭제는 성공·삽입은 실패하도록 가짜 COM에 오류를 주입했다. `도토리 ,만두`가 실제로 `도토리만두`로 바뀌었지만 반환 수정수는 0이었다. 다음 캐시 읽기는 여전히 `도토리 ,만두`였다.
- 삭제 후 삽입 실패로 글이 일부 없어지는 위험은 기존 규칙에도 있었다. **옛 텍스트를 후속 규칙에 공급하는 위험은 Beta 12 캐시로 추가**된다. 후속 위치 기반 편집이 잘못된 글자 범위에 적용될 수 있다.
- 제안: 편집 시도 전에 해당 문단 캐시를 무효화한다. 성공 건수와 별도로 `mutation_attempted`, `failed`, `partial` 상태를 반환하고, 부분 변경은 복원하거나 해당 문단을 중단·미해결로 기록한다.
- 필요한 시험: 성공·무변경·삭제 성공/삽입 실패·부분 다중 치환·문단 이동·취소 각각에서 다음 규칙이 읽는 글과 실제 글이 같아야 한다. 현재 캐시 테스트 3개는 읽기 횟수·수동 비우기·캐시 꺼짐만 확인한다.

### R3 · P1 · 회귀 도구가 시험 모드·품질을 정확히 대표하지 못함

- 위치: `scripts/regression_pc.py:63`, `65`, `139`, `151`; 앱 설정은 `hwp-auto-docfit.py:1294`, `17675`.
- 앱이 쓰는 키는 `all_include_spacing`인데 도구는 `include_spacing`을 읽는다. 사용자가 자간 조정 포함을 꺼도 키가 없으면 `all`로 실행한다. `stage_choices`도 저장값 대신 기본 단계로 구성한다. “저장된 설정 그대로”라는 설명과 다르다.
- 실행 모드는 `all/format`뿐이다. `--require-same-layout` 설명은 서식 통일의 원본 쪽 구성 유지 시험용인데 **`unify` 실행을 선택하는 인자가 없다**. 현재의 서식 통일 카드 정책을 그대로 검증할 수 없다.
- 합격 판정은 결과 파일 생성 중심이고 점수·본문 보존·표 구조 보존을 보지 않는다. 쪽 비교 미실행인 `layout_same=None`도 `--require-same-layout`에서 통과한다. 실제 반환식에 `output_created=True, score=None, layout_same=None`을 넣으면 종료 코드 0이었다.
- 쪽 나눔 개수가 `보고서 수−1` 이하여야 한다는 조건은 Beta 11/12에서 허용하는 **표 제목 묶음의 쪽 나눔**을 반영하지 않아 거짓 실패도 가능하다. 쪽 나눔을 위치/역할별로 평가해야 한다.
- `--beta-mode`는 `알파_…_사용` 플래그를 전부 끈다. Beta 12에도 이 이름의 캐시가 들어 있으므로 **이 옵션이 곧 Beta 12라는 의미는 아니다**. JSON의 alpha/beta 표기를 실제 버전/커밋/플래그로 바꿀 필요가 있다.
- 제안: `--mode unify|format|all|spacing`, 명시적인 설정 스냅샷, 해당 모드의 저장 단계 적용, pass/fail/not_run/not_applicable 상태를 도입한다. 비교를 요구했는데 비교가 없으면 성공으로 처리하지 않는다.

### R4 · P2 · 일시적 읽기 실패가 빈 문단으로 캐시됨

- 위치: `hwp-auto-docfit.py:14331`, `14339`.
- `_현재문단_텍스트_읽기`는 COM 읽기 실패와 실제 빈 문단을 모두 `""`로 돌려준다. 캐시층은 이 값을 정상 결과로 저장한다.
- 첫 GetText만 실패하고 다음 읽기는 성공하도록 오류를 주입했지만, 두 번 읽기 모두 빈 문자열이고 실제 COM 읽기 시도는 1회였다. 해당 문단의 후속 정규화 규칙이 모두 건너뛰어질 수 있다.
- 제안: 성공 여부와 글을 분리해서 반환하고, 읽기 실패는 저장하지 않는다. 제한된 재시도 후에도 실패하면 검수에 미검사 문단을 남긴다.

### R5 · P2 · 업데이트의 복구 범위는 교체 실패까지이며 새 앱 시작 실패는 확인하지 않음

- 위치: `docfit_core/updater.py:70`~`73`, 앱 시작의 `업데이트_잔여정리`, `leftover_files`.
- `Start-Process` 뒤 2초를 기다리고 백업을 지운다. 새 프로세스가 정상 UI 초기화까지 갔는지, 즉시 종료했는지 확인하는 성공 신호가 없다. 앱 시작 시 정리 스레드도 백업 삭제를 시도한다.
- 따라서 “교체 단계 실패 시 복원”은 구현돼 있지만 “새 버전 실행 실패까지 복구”로 설명하면 범위가 과장된다. 이번에는 실제 앱 크래시를 재현하지 않고 코드 경로로 확인했다.
- 제안: 새 앱 정상 시작 확인 파일/신호 이후 백업 제거, 확인 실패 때 명시적인 복원 경로. PowerShell 실행 직후 잠깐 살아 있다는 조건만으로 충분하지 않다.

## 4. 성능 기준 재평가

기존 `docs/benchmarks`의 Beta 11 기준 문서와 Beta 12 릴리스 노트를 재검토했다. **아래 시간은 이전 PC 실측 기록이며 이번 리뷰에서 문서를 다시 처리해 측정한 값이 아니다.**

| 입력·측정 | Beta 11 | 캐시 적용 코드(Beta 12 포함) | 기록에서 말할 수 있는 범위 |
|---|---|---|---|
| 보고서 예시 TXT, 교차 3회 | 179.4·179.6·180.0초, 중앙값 179.6초 | 168.5·168.6·171.0초, 중앙값 168.6초 | 이 조건에서 −11.0초, 약 −6.1%. 점수 100·3쪽·수정 건수 동일 |
| 14쪽 입력, 표 제외, 각 1회 | 366.9초 | 351.4초 | 관측 −15.5초, 약 −4.2%. 3회 중앙값 또는 일반 성능 향상률로 부르면 안 됨 |

14쪽 입력의 결과는 기록상 두 경로 모두 21쪽·점수 100이다. 이는 **경로 간 같은 결과**이지 **원본 14쪽을 유지했다는 증거가 아니다**. 서식 적용/한 번에 적용의 작업 목적에 맞춰 판정해야 한다.

TXT 예시의 3쪽 결과도 입력 TXT의 원본 쪽 구성 유지 시험이 아니다. 점수·쪽 수·수정 건수 동일만으로 글/표/개체/강조가 모두 동일하다고 확정할 수 없다. `smoke_batch_format.py`의 본문 해시·표/그림 수 비교를 같이 사용하되, 그 값도 셀별 내용·서식·시각 동일성 전체를 대신하지 않는다.

Beta 11 기준 첫 회의 시간 비중은 자간/줄 끝 53.9초(약 30%), 서식/기타 35.3초(약 20%), 쪽 맞춤/배치 30.1초(약 17%), 내어쓰기 28.4초(약 16%), 저장/검수 19.6초(약 11%), 열기/변환 9.4초(약 5%)다. 합계는 반올림 때문에 전체와 약간 다르다. 공백 정규화 12.8초는 별도 세부값이므로 다시 합산하지 않는다.

**추가 XML 서식 개선을 전체 시간의 대다수 절감으로 주장할 수 없다.** 이미 적용된 캐시 뒤의 단계별 시간, 캐시 hit/miss·읽기 실패·XML 적용률·폴백 수를 측정하고 남은 병목을 선택해야 한다.

현재 kordoc 브리지는 여전히 `kordoc@^4`, `npx -y`, Node 18 안내이며 upstream은 Node 20 이상이다. 코드 검증 당시 버전이 실행 시점에 달라질 수 있으므로 외부 엔진 결과를 베타 품질로 연결하기 전에 계약을 고정해야 한다.

auto-hwp의 타입 명령은 오류를 조용히 성공으로 삼키지 않는 계약이 참고점이다. 다만 상세 문서에는 일부 에러가 코드 없는 문자열이라고도 명시하므로, 모든 계약을 완성 사례로 그대로 받아들일 수는 없다. rhwp/auto-hwp의 조판 수치와 kordoc 표 구조 수치를 Beta 12 후처리 속도 순위로 환산하지 않는다.

## 6. 다시 정한 실행 순서와 합격 기준

1. **R1/R2/R3부터**: PID 통합 시험, 편집 부분 실패 시 캐시 무효화·복원, 회귀 도구의 모드·설정·판정 정합성을 먼저 확보한다. R4는 캐시 수정과 함께 처리한다.
2. **결과 계약 통일**: 완료/부분 적용/실패/미검사/대상 아님을 코어·브리지·최종검수·회귀 JSON에서 같은 의미로 사용한다. 파일이 존재한다는 이유만으로 품질 합격을 주지 않는다.
3. **Beta 12 기준선 고정**: 원본 파일 해시·코드 SHA·EXE SHA·한/글/Windows/글꼴·설정 스냅샷·작업 모드·단계 목록·표 제외를 기록한다. 베타 플래그 이름만으로 버전을 식별하지 않는다.
4. **모드별 코퍼스 측정**: 서식 통일+원본 유지, 서식 적용, 한 번에 적용, TXT→HWPX 생성을 나눈다. 동일 문서 교차 3회 중앙값, 실패율·부분 적용률과 품질 기준을 함께 기록한다.
5. **필요한 단계만 확대**: 사용자 서식·괄호/라벨 구간·표 서식 순으로 XML 적용률을 측정하며 확대한다. 모든 문단을 COM에서 제거하려 하지 않는다. 조판 의존 단계는 한/글 실측을 유지한다.
6. **감마는 별도 실험**: 같은 공개/가상 문서의 줄 위치·쪽 수·표/개체·폰트·이미지를 한/글 참조와 비교한다. 현재 문서에 대한 시각 동일성 미확인을 명시한다.

독립 품질 검증 예:

| 작업 | 합격 조건 |
|---|---|
| 서식 통일+원본 유지 | 본문/표 셀/개체 보존, 보고서별 시작·끝 쪽과 전체 쪽 수, 허용된 쪽 나눔의 위치/역할 |
| 서식 적용·한 번에 적용 | 요청 서식·가독성 규칙 준수, 내용 보존, 묶음 분리·미해결 어절 증가 없음. 원본 쪽 수 동일을 자동 강제하지 않음 |
| TXT 생성 | 원고 사실·숫자·표 누락 없음, 한/글 열기·실제 결과 페이지 검토. 원본 쪽 비교는 대상 아님 |
| 캐시 ON/OFF 비교 | 수정 결과·위치·서식·미해결 상태 동일. 부분 실패·일시 읽기 실패에서도 정확성 유지 |
| 외부 생성기 연계 | 생성기 자체 품질과 Beta 12 후처리 효과를 따로 측정. 사실/기관/날짜 잔재와 조판 변화 확인 |

## 7. 검증 결과와 조사 한계

- 전체 Windows 단위 시험: `.venv\Scripts\python.exe -m unittest discover -s tests` → **773개 통과(329.188초)**. 시험 시작 뒤 갱신된 릴리스 커밋은 Python/테스트 코드를 바꾸지 않아 최종 리뷰 대상에도 적용된다.
- 실제 Beta 12 함수 추출 오류 주입: 부분 편집 캐시 불일치, 읽기 실패 빈값 캐시를 확인.
- 실제 Windows PowerShell 안전한 매개변수 시험: 쉼표 PID 문자열이 배열로 전달되지 않음을 확인.
- 실제 회귀 도구 반환식 평가: 미검사 쪽 비교·점수 없음도 성공으로 반환함을 확인.
- EXE 해시와 릴리스 노트 일치 확인. EXE를 실행해 UI/COM 조판을 새로 검증하지는 않았다.
- 단위 시험 중 Tk 예약 콜백 `invalid command name … (after script)` 출력이 관찰됐다. 전체 unittest 판정과 분리해 기록한다.
- 기존 실측의 −6.1%/−4.2%는 출처 기록을 재평가한 수치다. 이번 재현은 실패 경로 검증이며 성능 재측정으로 표시하지 않는다.
- 외부 프로그램 코드는 옮기지 않았고, 사용자 원본 문서는 열거나 변경하지 않았다.

**재평가 결론**: Beta 12는 XML 선적용과 실측 성능 개선을 이미 확보했다. 지금의 벤치마킹 중심은 범용 기능 수 증가보다 **부분 실패를 안전하게 처리하고, 작업 모드에 맞는 독립 품질 검증으로 개선 효과를 증명하는 것**이다.
