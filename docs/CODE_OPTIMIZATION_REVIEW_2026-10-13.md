# 전체 코드 리뷰 및 최적화 검토 (2026-10-13)

## 결론과 범위

우선순위는 **본문 손실 방지 → 안전한 파일/설정 처리 → 반복 I/O와 UI 조회 축소 → UI·문서 엔진 분리**다. 한/글 COM 호출을 병렬화하거나 안전 검사를 제거하는 최적화는 권장하지 않는다. 이미 도입한 XML 일괄 서식, 단계별 시간 측정, 원본 보존 쓰기, Flutter 요청 수명/오래된 응답 방어는 유지한다.

검토 기준은 `alpha`의 `6728110`과 진행 중인 AI 붙여넣기 변경이다. 공개 Beta 1은 수정하지 않았다. Python 앱·브리지·`docfit_core`·`docfit_app`·`scripts` 84개 파일/43,301줄을 구문 분석하고 의존·예외·I/O 경로를 조사했다. 핵심 문서/저장/변환/통신 경로는 코드를 직접 확인했다. Flutter `lib` 8개 파일/3,007줄, Windows 빌드·GitHub/GitLab CI·리셋 도구·테스트 구성도 검토했다. 생성 Flutter 자산과 외부 SDK의 내부 코드는 자체 앱 코드 수에 포함하지 않았다. 모든 줄의 실행 결과나 모든 가능한 입력을 검증했다는 뜻은 아니다.

Linux Python 3.12/Flutter 3.47.5 환경이다. Windows+한/글 2020 COM 처리 시간, 실제 조판, WebView2 메모리, EXE 실행은 측정하지 못했다. 아래 성능 수치는 로컬 합성 자료의 결과이며 실제 공문 처리 속도 개선율은 아니다.

## 재현과 성능 근거

### 본문 보존

현재 개발 코드에서 직접 호출한 결과:

```text
clean_pasted_text("`items[1]`") → "items"

ai_answer_to_outline_text("```python\nitems[1]\nx = 2**3**4\n```")
→ "□ items\n\n□ x = 2**3**4"

입력: ## 안내 / - 정비를 추진합니다. / 더 궁금하신 사항은 담당자에게 문의해 주세요.
출력: □ 안내 / ㅇ 정비를 추진합니다.

입력 코드: <strong>내용</strong>
출력: □ 내용
```

`3 > 2, 2 * 3 = 6`은 이번 예시에서 보존됐다. 하나의 성공 예시를 모든 수식 보존으로 일반화하지 않는다. 사용자 제공 공백·이스케이프 강조/HTML 문자 참조 문제의 수정은 회귀시험을 통과했지만 위 보호 범위 문제까지 해결한 것은 아니다.

### 원본 보존 ZIP 경로

임시 폴더에 header/section과 4MiB의 반복문자 압축 항목을 만든 결과, 일반 `validate_hwpx`는 압축률 제한으로 거부했지만 `PackageSnapshot.load(...).read(...)`는 4,194,304바이트를 반환했다. 크기를 작게 제한해 재현했으며 대형 압축폭탄을 실행하지 않았다.

중복 없는 합성 ZIP을 각각 3회 snapshot으로 읽은 중앙값:

| 항목 수 | 현재 읽기 시간 |
| --- | --- |
| 1,000 | 41.86ms |
| 2,000 | 266.78ms |
| 4,000 | 997.95ms |

파서 전체 시간에 런타임/메모리 비용도 포함된다. O(n²) 근거는 코드의 반복 집합 생성이며, 측정값은 그 비용이 커지는 사례다. `seen` 변경 후 같은 자료로 다시 비교해야 개선율을 보고할 수 있다.

기존 `scripts/benchmark_ai_markdown.py`의 6사례에서는 경로 판정 오류·검사 대상 Markdown 잔여가 없었다. 최대 측정 중앙값은 1,898자 입력에서 19.951ms, 해당 Python 추적 메모리 최고값은 55,757바이트였다. 작은 fixture 성능이며 장문, 브라우저, HWPX 생성이나 COM 성능을 대표하지 않는다.

## COM·XML 최적화 방향

현재 단계별 시간 측정(`hwp-auto-docfit.py:5163`)과 XML 일괄 서식(`docfit_core/batch_format.py:355`)이 이미 있으므로 새 최적화 전에 이를 이용한다. 문서 크기뿐 아니라 표·병합셀·그림·쪽 범위·서식 종류로 코퍼스를 나누고 각 단계의 중앙값/p95, COM 호출 수, SaveAs/재열기 횟수, peak memory를 기록한다.

문서별 작업 컨텍스트 안에서 헤더/섹션 파싱 결과, 서식 ID 맵, 셀 텍스트·폭 계산을 재사용하되 문서 변경 후 무효화한다. 변경 없는 단계는 저장/재열기를 생략하고 순서상 결합 가능한 XML 단계만 한 snapshot에 적용한다. `validate_hwpx`의 안전 검사와 새 결과 검증은 유지한다. 줄 수·쪽 배치는 한/글 실제 조판으로 확인하고 오래된 XML lineseg 정보로 대신하지 않는다.

한 COM 인스턴스에서 여러 스레드가 문서를 동시에 수정하는 방식은 피한다. 공통 전역 `hwp`·작업 상태의 분리는 순차 실행을 먼저 보장한 뒤 진행한다. 독립 순수 분석만 worker로 옮기고 GUI 상태 반영은 Tk 이벤트 스레드에 둔다.

## 실행 순서와 검증 기준

1. **본문 보존 안정화:** 보호 범위/공문 안내 보존, 실제 사용자 원문과 코드/수식/법령 fixture. 변환 전후 유효 문자·수치·담당자 대조.
2. **저장·입력 안전성:** 설정 단일 writer, snapshot 공통 제한, 고유 임시 파일. 실패·크기 제한·동시 요청·원본 비수정 시험.
3. **낮은 비용 최적화:** ZIP `seen`, 중복 CRC 제거, 문서 작업 내 파싱 재사용. 동일 자료로 측정하고 결과 구조/원본 해시 비교.
4. **Flutter 상태 비용 축소:** revision·진행상태 분리, idle polling 완화. 늦은 응답·입력 draft·작업 종료·연결 실패 위젯 시험.
5. **Windows 검증:** 문서 사본으로 한 번에 적용, 직함·이름 단위 자간 조정, 실제 조판/저장 재열기, 중단/종료, EXE 자산. 동일 PC/한글 버전에서 수정 전후 비교.
6. **서비스 추출/재현 빌드:** 작은 단위로 이전하고 성능·결과 회귀 확인. MCP 전용 오메가는 별도 예정 범위로 유지.

이번 요청은 리뷰·보고이므로 위 최적화를 일괄 적용하지 않았다. 진행 중인 붙여넣기 수정·전체 Flutter 이관·직함/이름 자간 규칙은 별도 개발 작업으로 남아 있다. 실제 측정 없이 “속도 몇 % 향상”이나 “전체 오류 해결”을 주장하지 않는다.
