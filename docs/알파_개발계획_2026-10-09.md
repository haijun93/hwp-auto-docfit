작성: 2026-10-09 · 대상: `alpha`(신기술 시험 트랙, COM 기반) · 관련: `docs/종합검토_알파감마_개발방향_2026-10-09.md`, `TODO.md`

> 근거 수준 표기: **실측**(사용자 PC 로그·실제 파일), **코드**(소스·커밋 확인), **추정**, **미확인**.
> 이 계획을 쓴 환경은 Linux라 한/글을 실행하지 못했다. 한/글 동작은 모두 사용자 PC 실측이 필요한 가설로 다룬다.

## 1. 요약

1. **목표**: 알파는 계속 **정확도 우선의 서식 자동화 심화(A안)**를 맡고, XML로 할 수 있는 일은 XML로 옮겨 **COM 호출을 줄이며**, 순수 로직을 `docfit_core`로 모아 **감마(MCP)와 코드를 공유**한다.
2. **합격 기준**: 사용자가 정한 **쪽 구성 동일 원칙** — 결과의 보고서별 쪽 범위·전체 쪽 수가 원본과 같을 것(2026-10-09). 최종검수 점수와 미해결 문단 수가 함께 본다.
3. **지금 가장 급한 일**: ① 브랜치 통합(쪽 맞춤 작업과 알파 XML 일괄 서식이 따로 있음), ② 쪽 구성 동일 원칙의 남은 실패 사례 마감, ③ 붙임 쪽 감지.
4. **순서**: 반복 0 통합 → 1 쪽 구성 마감 → 2 내어쓰기·라벨 서식 → 3 XML 경로 확장·측정 연구 → 4 서식 프리셋·스타일 검수·생성물 연계. 반복마다 **사용자 PC 실측 1회(번들)**로 끝낸다.
5. **처리 구조를 "2단계 파이프라인"으로 정식화한다(W7, 2026-10-09 사용자 제안)**: **1단계 = 서식을 HWPX XML에서 한꺼번에 적용**(korean-report-hwpx처럼 빠르게), **2단계 = 한/글을 한 번 열어 조판에 의존하는 일(내어쓰기 → 자간 조정 → 쪽 맞춤 → 검수)만 COM 실측으로 처리**. 알파 1.73 Alpha 1의 XML 일괄 서식이 이미 이 구조의 시작이고, 계획은 그 범위를 넓혀 기본 구조로 만든다.
6. **하지 않는 것**: 감마가 맡는 일(알파 MCP·크로스플랫폼), 근거가 약한 백로그(스킨·갤러리·스티커 메모·실시간 미리보기)는 보류하고, 스티커 메모는 폐기를 권고한다.

## 3. 원칙

1. **쪽 구성 동일**: 어떤 처리를 해도 보고서별 쪽 범위·전체 쪽 수는 원본과 같아야 한다. 모든 시험의 합격 기준.
2. **정확도 우선, 실측 기준**: 조판에 의존하는 값(내어쓰기·자간·쪽 배치)은 계산하지 않고 한/글에 묻는다. 추측용 `lineseg`는 알파에서 쓰지 않는다.
3. **XML 먼저, COM은 조판 확인에만(2단계 파이프라인)**: 서식 적용처럼 조판과 무관한 일은 XML 일괄 적용(`batch_format.py` 방식)으로 먼저 끝내고, 그 결과를 한/글이 **한 번 열어 다시 조판**한 뒤 내어쓰기·줄 끝·쪽 배치 실측만 COM으로 한다. 상세는 W7.
4. **순수 로직은 `docfit_core`로**: 한/글 없이 시험되는 로직(`page_fit_search.py`처럼)은 코어에 두어 Linux에서 시험하고 감마와 공유한다. 앱 본체(`hwp-auto-docfit.py`, 약 22,600줄)는 얇게 만든다.
5. **원본 불변, 사본 시험, 기록**: 모든 과제는 단위 시험 + 사본 실측 로그 + `TODO.md` 기록으로 닫는다. 업무 문서는 저장소에 넣지 않는다.
6. **한 번에 한 가지 변경**: 변경마다 켜고 끄는 설정 플래그를 두어 회귀 시 즉시 되돌린다(`페이지맞춤_고속_사용` 방식).

### W7. 2단계 파이프라인: XML 서식 선적용 → 조판 단계 (반복 0 시작, 1~4에 걸쳐 확대)

**제안(사용자, 2026-10-09)**: korean-report-hwpx MCP처럼 서식을 신속히 적용한 뒤, 내어쓰기·자간 조정·페이지 맞춤을 적용한다. 속도 개선이 목적이다.

**현재 구조(코드)**: `문서_처리_1회`의 단계 순서는 이미 대략 *서식통일 → 표준서식·괄호/라벨 → 표 서식·셀 여백·너비·테두리 → 한 칸 표 자간 → 최종 내어쓰기 → 부연설명 들여쓰기 → 별표 정렬 → 공문 띄어쓰기 → 본문 자간·단어 분리(반복) → 짧은 마지막 줄 → 표/컨트롤 자간 → 자간 후 내어쓰기·부연설명 재적용 → 쪽 맞춤 → 개별 문단 페이지 배치 → 재확인*이다. 순서는 맞고, **서식 단계가 문단마다 COM을 호출하는 것**이 속도의 걸림돌이다. 1.73 Alpha 1은 그중 "기본 보고서 서식의 단순 본문"만 XML(`표준서식_hwpx_처리` → `apply_batch`)로 옮겼다.

**korean-report-hwpx와 다른 점**: 그쪽은 문서를 **생성**하므로 XML이 곧 결과이고 줄 끝은 폭 추정이다. 알파는 **기존 문서를 고치므로** 내용·개체·강조를 보존해야 하고, 줄 배치는 한/글 실측으로 확정한다. 그래서 같은 "서식 선적용"이어도 복잡한 문단은 COM 폴백, 적용 뒤 무결성 검사가 필요하다.

**단계 분류표**

| 구분 | 단계 | 이유 |
|---|---|---|
| **1단계(XML, 조판 비의존)** | 문두기호별 글꼴·크기·장평·줄간격·굵게, 문단 위/아래 간격, 괄호·대괄호·문두 라벨 서식(구간 서식), 표 서식·셀 여백·너비·테두리(C1~C3), 제목·개요·붙임 서식 표, 서식통일의 교정(대표값 산출은 읽기), 준말 변환, 공문 띄어쓰기·문두 점 기호·붙임 번호 정리, 부연설명 앞 빈칸 | 글자·문단 속성과 글자 수 변경이라 줄 배치를 몰라도 결정됨 |
| **2단계(COM 실측, 조판 의존)** | 내어쓰기(Shift+Tab), 부연설명 왼쪽 여백(부모 실측), 본문 자간·단어 분리, 짧은 마지막 줄 병합, 표/컨트롤 자간, 쪽 수 맞춤, 개별 문단 페이지 배치, 최종검수 | 줄 시작·끝 위치와 쪽 경계를 한/글만 알려 줌 |

**과제**

| 과제 | 내용 | 합격 기준 |
|---|---|---|
| W7-0 | **전 단계 계측**: `stage()`(한 곳)에서 단계별 소요를 로그로 남기고 문서 끝에 합계 표를 출력 | 이번 문서 처리 시간이 서식·내어쓰기·자간·쪽 맞춤·검수 중 어디에 쓰였는지 숫자로 확인. **효과 예측의 전제** |
| W7-1 | 위 분류표를 코드의 단계 목록에 대응시켜 확정(각 단계 XML 가능 여부·선행 조건·위치 맵 필요성) | 단계마다 1/2단계 지정 |
| W7-2 | 1단계 범위를 순서대로 확대: ① 표준서식(확대) ② 괄호·대괄호·라벨 ③ 표 서식(C1~C3) ④ 제목·개요·붙임 표 ⑤ 서식통일 교정 ⑥ 공백·띄어쓰기·부연설명 앞 빈칸 ⑦ 문단 간격 | 단계마다 기존 경로와 **서식 결과 동일**(비교 도구), XML 적용률 상승 |
| W7-3 | 1→2단계 인터페이스: 1단계가 적용한 문단 목록·위치를 2단계에 넘겨 **중복 적용 생략**, 복잡한 문단(컨트롤·필드·표 안)은 COM 폴백으로 표시. 한/글은 1단계 결과를 **한 번만 열고** 낡은 줄 정보는 지워 둔다(`batch_format`이 이미 `linesegarray`를 제거) | 폴백 문단도 서식 누락 없음, 본문 일치도 100% |
| W7-4 | 2단계 최적화(측정 후 결정): **내어쓰기 사전 기입 + 실측 검증**(1단계에서 공식으로 예측 기입하고 2단계는 어긋난 문단만 실측 보정), 내어쓰기↔자간 순환 의존 정리(내어쓰기 → 자간 → 내어쓰기 최종 → 쪽 맞춤 유지), 한 줄 문단 생략 확대 | 정확도 동일(오차 0), 시간 단축 |
| W7-5 | 정확도 가드: 1단계 직후 XML과 한/글 `GetText` 본문 일치 확인, 쪽 구성 동일 원칙 유지, 설정 플래그 `파이프라인_2단계_사용`으로 기존 경로로 즉시 되돌림, 기존 경로 대 신규 경로 비교(`scripts/smoke_batch_format.py` 확장) | 비교 결과 서식·쪽 구성 차이 0 |

**기대 효과(정량은 보류)**: 절감 시간 ≈ (1단계로 대체되는 COM 서식 단계 시간) × XML 적용률 − (저장·재열기 비용). 이번 문서(23쪽, 표 제외, 전체 317.5초 중 쪽 수 맞춤 약 67초)에서 나머지 약 250초가 어느 단계인지 W7-0 계측 전에는 모른다. 1.73 Alpha 1도 "실제 문서 전체의 속도 향상은 Windows 검증이 필요"로 명시돼 있다. 따라서 **수치 목표는 계측 후 확정**한다.

**위험**
- 1단계 범위가 좁으면(복잡한 문서) 폴백이 많아 이득이 작다 → **XML 적용률**을 지표로 관리한다.
- XML 서식과 COM 서식이 미세하게 달라질 수 있다(글자 모양 ID 공유, 강조·위첨자 보존) → 비교 도구로 서식 동일성 확인.
- 1단계가 문단 수·순서를 바꾸는 단계(빈 줄 삽입·삭제)는 위치 맵이 깨지기 쉽다 → 구조 변경 단계는 맨 뒤(⑦)에 두고 신중히.
- 내어쓰기 사전 기입은 정확도 회귀 위험 → 실측 검증으로 어긋난 문단만 고치므로 정확도는 지키되, 어긋남 비율이 높으면 이득이 없다.

## 9. 이 계획의 한계

- 한/글을 실행하지 못한 환경에서 쓴 계획이다. 원인 추정(자간 초기화, 첫 줄 공백 신장)은 PC 실측으로 확인해야 한다.
- 쪽 구성 동일 원칙 적용 이후의 최신 실측은 7쪽 문서 한 건이 전부다. 14쪽·10보고서 문서와 표 묶음 분리의 현재 상태는 확인하지 못했다.
- 병합 가능성은 텍스트 충돌 유무만 확인했고 동작 충돌은 시험으로 확인해야 한다.
- 난이도는 상대적 표기이며 일정(기간) 약속이 아니다.
