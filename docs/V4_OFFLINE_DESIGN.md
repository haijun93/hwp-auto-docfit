# v4.0 설계 — 폐쇄망 문서 자료함과 로컬 검색

작성: 2026-11-02  
상태: 설계 초안. 사용자는 온라인 LLM뿐 아니라 **로컬 LLM도 사용할 수 없는 폐쇄망 PC**를 전제로 검토를 요청했다. 이 문서는 이 제약을 제품 범위의 기본값으로 삼는다.

## 목표와 제외 범위

v4.0은 한글편집 후처리를 문서 작업 도구에서 **업무 자료를 모아 찾고, 근거 위치가 있는 검토 기록을 남기는 오프라인 작업공간**으로 확장한다. 핵심 가치는 문서 파일에 대한 정확한 로컬 키워드 검색과 반복 작업의 재현성이다.

온라인 API, 로컬 LLM, 임베딩 모델, 의미 기반 검색, AI 대화·요약·분류·팟캐스트, 클라우드 동기화는 v4.0에 포함하지 않는다. 명시된 규칙을 적용하는 결정론적 기능만 제공한다. “AI처럼 답을 이해한다”는 표현을 사용하지 않으며, 검색은 검색어 일치 결과를 반환한다.

## 사용자 흐름

1. 사용자가 업무 자료함을 만들고, 포함할 폴더를 직접 선택한다.
2. 앱은 선택된 경로 아래 허용 형식만 증분 검사한다. 이름·경로·크기·시간 메타데이터를 먼저 색인하고, 본문 검색을 켠 경우에만 지원 형식의 텍스트를 로컬에서 추출한다.
3. 자료함에서 파일명·본문 검색, 형식·폴더 필터, 최근 수정 정렬을 사용한다. 결과에는 문서명과 가능한 경우 쪽·문단 또는 표 행·열을 표시한다.
4. 사용자가 검색 결과를 열어 확인하고, 해당 위치를 가리키는 검토 메모를 직접 작성해 저장한다.
5. 저장된 작업 프리셋으로 문서 정리 옵션을 재적용하고, 결과 파일은 기존 정책대로 원본 옆의 새 파일로 저장한다.

## 기능 설계

### 1. 업무 자료함

- 자료함은 사용자가 정한 이름·설명·색인 대상 폴더·허용 확장자 집합으로 구성한다. 한 파일을 여러 자료함이 참조할 수 있으며, 파일을 복사해 별도 보관하지 않는다.
- 기본 폴더는 자동 수집하지 않는다. 첫 실행에서 폴더 선택과 하위 폴더 포함 여부를 사용자가 확인한다. 네트워크/이동식 경로는 기본 제외하고 명시 선택 시 상태를 알린다.
- 타임머신의 SQLite·폴더 선택·증분 스캔 코드를 참고하되 기존 `timeline.db` 스키마와 의미를 섞지 않는다. 새 DB `workspace/library.db` 또는 앱 데이터 폴더의 동등한 전용 경로를 둔다.
- 자료함 삭제는 색인·메모 삭제 여부를 확인한다. 원본 문서는 절대 이동·삭제하지 않는다.

### 2. 키워드 본문 검색

- 1차 파일명 검색은 현재 타임머신 색인으로 제공한다. 본문 검색은 HWPX, TXT, MD, PDF 등 **현재 내장 추출기로 검증된 형식만** 순차 지원한다. HWP(바이너리), 암호·DRM 문서, 이미지 OCR은 명시적으로 미지원/미색인 상태를 표시한다.
- HWPX는 기존 안전 ZIP 검사와 `defusedxml` 경로를 재사용한다. 본문 문단과 표 셀을 추출하고 섹션·문단 번호 및 표 번호·행·열을 위치 메타데이터로 보존한다. PDF는 내장 PDF 텍스트 추출 가능 여부를 확인해 텍스트층이 있을 때 색인한다. OCR 엔진이 포함되어도 OCR 색인은 정확도·폐쇄망 모델 배포·처리시간을 별도 검증하기 전까지 기본 범위에서 제외한다.
- SQLite FTS5 사용 가능성을 빌드 대상 Windows `winsqlite3.dll`에서 확인한다. FTS5가 없으면 같은 스키마 경계 안에 정규화 토큰/일치 검색 대체 구현을 두고 기능을 비활성화하지 않는다. 한글 형태소 분석기를 전제로 하지 않는다. 공백 분리·부분 문자열·정확 구문 검색의 범위를 UI에 설명한다.
- 문서가 바뀌었을 때만 재추출한다(경로·크기·mtime·필요 시 내용 해시). 한 파일 실패가 전체 스캔을 멈추지 않으며, 오류·암호·미지원·클라우드 전용 상태를 항목별로 기록한다. 사용자는 폴더별/자료함별 재색인 및 전체 색인 삭제를 수행할 수 있다.
- 처음에는 본문 색인을 선택 기능으로 제공하고 기본값은 **끔**으로 둔다. 색인할 폴더·형식·예상 로컬 저장 위치와 디스크 사용량을 사전에 안내한다.

### 3. 근거 연결 메모

- 메모는 사용자 작성 텍스트이며, 파일 참조·자료함 ID·위치(섹션, 문단, 표/셀)·원문 스냅샷이 아닌 짧은 인용 문자열을 선택적으로 가진다.
- 원문이 이동·삭제되면 메모를 보존하고 참조 끊김을 표시한다. 메모 검색은 본문 검색과 분리된 단순 검색으로 지원한다.
- 입력 문서에서 개인정보가 추출될 수 있으므로 미리보기/검색 결과는 선택된 폴더만 대상으로 한다. 진단 로그에는 본문·검색어·메모를 기록하지 않는다.

### 4. 작업 프리셋

- 기존 문서 정리의 세부 옵션을 명명된 설정 묶음으로 저장·복제·내보내기/가져오기 한다. 프리셋은 실행 코드나 임의 명령이 아니라 검증된 설정 스키마만 담는다.
- 실행 전 대상 파일·출력 이름·적용 옵션을 보여주고 사용자가 시작한다. 실패·취소 시 원본 무변경을 보장하고 작업 결과를 요약한다.
- 기본 제공 프리셋과 사용자 프리셋을 분리한다. 가져온 JSON은 크기·스키마·값 범위를 검증하고 알 수 없는 키를 거부한다.

## 구조와 데이터 경계

- **실행 형태 결론**: 상시 백그라운드 실행은 최적 최소 자원이라는 목표에 도움이 되지 않는다. 따라서 v4.0 자료함은 처음부터 독립 상주 프로세스로 만들지 않는다. UI/색인 작업을 주 앱에서 **요청 시 실행(on-demand)** 하고, 창을 닫거나 작업이 끝나면 작업 스레드를 정리한다. 대규모 색인은 낮은 우선순위·청크 단위·취소 가능으로 구현한다.
- **KAgent 경계**: 몽땅클립보드는 클립보드 변경 이벤트를 받아야 하므로 상주 에이전트가 필요하고, 타임머신 감시는 이미 KAgent가 메타데이터만 저자원으로 처리한다. 본문 자료함 검색은 사용자가 검색/색인을 요청할 때만 파일을 읽으므로 상주 이득이 없다. KAgent에 본문·메모 색인을 넣으면 클립보드·파일 감시의 최소 코드/권한/감사 경계를 넓히고, 민감 본문이 장시간 프로세스 메모리에 머물 수 있어 권하지 않는다.
- **향후 별도 실행 파일**: 조직 정책이나 앱 UI와 독립된 예약 색인이 실제 필요로 확인되고, 작업 시간·자원 절감이 측정되면 독립된 **온디맨드 작업자 exe**를 별도 검토한다. 이는 상주 에이전트가 아니라 요청을 받아 한 번 실행하고 종료하는 작업자다. KAgent와 DB를 공유하지 않고 전용 library DB/API를 사용한다. 설치 파일에 동봉, SHA-256 검증, 서명/허용목록 심사, 프로토콜·스키마 호환성, 종료·취소·업데이트 복구 시험을 마쳐야 한다. 설계 초기에는 별도 exe로 분리하는 것이 유리하다고 단정할 근거가 없다.
- **자원 설계 목표**: 앱이 닫혔을 때 추가 상주 메모리·CPU·핸들·파일 읽기·디스크 쓰기 **0**. 사용자 요청 시 UI를 포함한 색인 작업의 추가 개인 메모리 목표는 기준 PC에서 50MB 이하, 유휴 대기 중 CPU 0.1% 미만으로 두되, 초기 성능 측정에서 확인 후 고정한다. 전체 재색인은 청크 처리하고 UI 프레임·검색 응답을 막지 않는다.
- 도메인: `docfit_core/library/`에 저장소 모델, 검색 쿼리·정규화, 인덱서 계약과 단위 시험을 둔다.
- 추출기: `docfit_core/library/extractors/` 아래 포맷별 추출기를 둔다. 포맷 추출 결과는 `{text, location, source_kind, warnings}` 형태이며, HWPX 기존 안전 읽기·PDF 텍스트 추출기를 재사용한다.
- 서비스: `docfit_app/library_service.py`가 자료함·검색·색인 작업·취소·진행 상태·메모를 제공한다. IPC에는 파일 경로를 임의로 허용하지 않고 자료함 허용 루트 안인지 매번 검증한다.
- UI: Flutter에 자료함 목록, 검색, 검색 결과 위치, 메모 편집, 색인 상태/설정을 추가한다. 사용자가 요청하지 않은 백그라운드 자동 감시를 기본으로 켜지 않는다. 명시적으로 자료함을 열거나 “지금 색인”을 누를 때 증분 검사한다.
- 현재 `docfit_core.timemachine.Store`는 파일명·메타데이터용으로만 유지한다. 본문 텍스트를 timeline DB에 넣지 않는다. 자료함은 별도 DB와 정리/삭제 수명주기를 갖는다.

## 폐쇄망·보안 기본값

- 실행 중 외부 DNS/HTTP 요청, telemetry, 원격 폰트·스크립트, 온라인 모델 확인을 추가하지 않는다. 설치·업데이트는 기존 오프라인 런타임 정책을 따른다.
- 본문·메모·색인은 사용자 PC의 앱 데이터 아래 평문 SQLite로 남을 수 있다. DPAPI 암호화 여부는 저장 용량·검색 성능·복구 가능성을 비교하여 구현 전 결정하며, 보안 통제를 과장하지 않는다. 사용자에게 위치·삭제·백업 방법을 안내한다.
- 네트워크 경로 색인은 명시 동의 후에만 허용하고, 권한 오류/끊김에 대응해 중단·재시도할 수 있어야 한다. 심볼릭 링크·정션은 따라가지 않는다.
- 앱 로그와 오류 보고서에 문서 본문, 검색어, 메모, 사용자 경로를 넣지 않는다. 임시 텍스트 추출물은 작업 종료 시 삭제하고 crash-recovery 파일에도 본문을 남기지 않는다.
- 수동 업데이트 조회 같은 기존 인터넷 경로를 새 자료함 기능의 실행 경로에서 호출하지 않는다. 폐쇄망 네트워크 0회는 소스 점검뿐 아니라 PC/VM 네트워크 추적 시험으로 확인한다.

## 단계와 완료 기준

### 4.0-A — 오프라인 파일명 자료함

자료함 생성/편집, 지정 폴더, 기존 파일 메타데이터 증분 색인, 파일명 검색/필터, 열기/폴더 열기. 한 달·10만 파일 기준 타임머신 측정과 병행하되 서비스·DB는 분리한다.

### 4.0-B — 본문 키워드 색인

우선 HWPX·TXT·MD, 다음 PDF 텍스트층. 위치가 있는 결과, 진행/취소/오류 상태, 재색인/초기화. 실제 Windows SQLite FTS5 유무와 10만 문서·대형 HWPX 메모리/속도 실측 후 인덱스 구조 확정.

### 4.0-C — 메모와 인용 위치

사용자 메모 CRUD, 문서·위치 링크, 끊어진 링크 처리, 메모 검색·백업/복원.

### 4.0-D — 작업 프리셋

검증된 작업 설정의 저장·복제·가져오기·내보내기, 미리보기/확인, 작업 이력 연결.

## 검증 게이트

- Python: 경로 탈출·심볼릭 링크 거부, 원문 보존, 암호/손상/지원 외 형식 처리, 증분 재색인·중단 복구, SQLite 트랜잭션, 메모 참조 유실·복구, 검색 특수문자와 한글 입력을 단위·통합 시험한다.
- Flutter: 빈 자료함·오류·장시간 색인·취소·긴 파일명·420px/고 DPI·키보드 접근성을 검사한다.
- 성능 기준은 샘플 데이터 규모를 고정한 뒤 실측으로 확정한다. 초기 목표: 10만 파일 메타데이터 검색 p95 300ms 이하, 본문 검색 p95 1초 이하(전용 PC/데이터 사양 명시), 메모리 사용 상한 기록.
- Windows 실기기: 한/글 2020 설치·미설치 모두 확인하고 HWPX 본문/표 셀 위치를 직접 대조한다. 원본 SHA-256이 작업 전후 동일한지 확인한다.
- 폐쇄망 승인: 새 기능 사용 중 외부 연결 0회, 설치 실행에 온라인 의존성 없음, 색인 DB 경로·잔여 텍스트 임시파일 없음, 설정 백업/복원 성공을 확인한다.
- 단계별 검증과 사용자 피드백 이후에만 기존 `main`에 반영한다. 이 설계 초안 자체는 기능 구현·릴리스 승인이 아니다.
- 상주 효과가 없음을 확인: 앱 종료 상태에서 자료함 프로세스가 남지 않고 CPU/메모리/핸들/파일 접근이 0인지 확인한다. 검색 중에는 취소 반응 시간과 UI 정지, peak working set을 측정한다. 이 목표를 달성하지 못할 때만 온디맨드 별도 작업자 exe를 비용 대비 검토한다.

## 주요 위험과 미결정 사항

1. HWPX/PDF 추출의 실제 포맷 범위, 위치 안정성, PDFium/native 런타임 라이선스 및 성능 확인.
2. Windows 시스템 SQLite의 FTS5 지원 여부 확인. 미지원이면 호환 검색기 구현 비용과 한글 부분 일치 품질을 비교.
3. 자료함을 타임머신과 같은 폴더 설정에 연결할지, 별도 자료함으로 유지할지 사용자 검토 필요. 초안은 명시적 목적 차이 때문에 별도 DB·자료함을 제안.
4. 색인 전체 텍스트 저장은 검색 편의와 민감정보 잔존 위험이 맞바뀐다. 본문 색인은 opt-in으로 두되, 보존 기간·한 번에 지우기·기기 백업 정책은 구현 전에 확정.
5. 읽기 전용 공유 문서·OneDrive 파일 온디맨드·네트워크 공유는 자동 다운로드/접근 지연이 생기지 않도록 기본 제외 또는 명시 허용으로 둔다.
6. v4.0 버전 번호·배포 채널·기존 버전에서 사용자 DB를 이전하는 방식은 이 설계에서 확정하지 않는다.
7. 본문 색인은 트리거 기반 온디맨드가 기본이며 KAgent 상주 기능에 넣지 않는다. 독립 exe 필요성은 추후 실제 측정/기관 운영 요구가 있을 때 결정한다.

## Scrivener 기능 벤치마킹 (2026-11-02)

### 검토 범위와 근거

사용자가 제공한 기능·장단점 설명(2026-11-02)을 기준으로 v4.0 자료함에 옮길 수 있는 UX 개념을 재평가한다. Binder, Research 폴더, 분할 보기, Corkboard, Snapshots, Compile, 목표 추적과 함께 학습 곡선·컴파일 복잡도·협업 부재·플랫폼별 차이를 고려한다. 이 개발 환경에서는 공식 사이트 네트워크 요청이 프록시에서 `403 Forbidden`으로 차단되어 설명의 외부 사실 확인은 하지 못했다. 기능 상세·라이선스·현행 플랫폼 지원은 구현 전 공식 자료로 재확인한다. 외부 코드 복사 대상이 아니다.

### Scrivener의 장단점에서 얻는 제품 원칙

- **인기 요인(비선형 작업과 한 프로젝트의 맥락 유지)**은 자료함의 계층·순서 재배열·참고자료·메모 연결로 제한적으로 가져온다. 다만 이 앱은 장편 원고를 직접 쓰는 프로젝트 매니저가 아니므로 원고 작성 체계 전체를 재현하지 않는다.
- **학습 곡선과 복잡한 Compile 설정**을 경계한다. 자료함은 기본 목록/검색으로 시작하고 카드·분할·출력 같은 보기는 단계적으로 추가한다. 컴파일에 다양한 서식 설정을 한꺼번에 노출하지 않는다.
- **협업/동기화 부재**는 이 앱에서 해결할 과제가 아니다. 폐쇄망·단일 사용자 우선으로 로컬 DB 잠금·손상 복구·명시적 내보내기/백업을 다루며, 클라우드 동기화나 동시 편집을 넣지 않는다. 네트워크 공유 폴더의 다중 사용자 DB 편집은 지원하지 않는다.
- **플랫폼별 UI 차이·별도 라이선스**는 Windows 10/11 단일 배포 제품인 현 앱의 직접 벤치마킹 대상이 아니다. v4.0의 교훈은 자체 DB 스키마와 내보내기 형식을 문서화해 사용자가 장기 자료를 회수할 수 있게 하는 것이다.

### 결론 및 v4.0 범위 조정

Scrivener에서 가장 잘 옮겨올 수 있는 것은 AI가 아니라 **비선형 분류·자료 보관·검토 상태 정리**다. 4.0-A는 Binder형 계층과 Outliner형 목록, 검토 순서 재배열을 핵심으로 한다. 저장 검색은 후속으로, Corkboard·Split Screen은 메모와 자료가 쌓인 뒤 필요성을 측정해 도입한다. 스냅샷은 별도 원문 복제보다 기존 원본 보존 정책·결과 파일 링크·선택적 비교로 해석한다. Compile은 사용자의 좁은 선택 결과/인용/출처를 내보내는 수준만 후속 조사하고, 범용 출판 조판기는 v4.0 필수 완료 범위에서 제외한다.

Scrivener의 긴 원고 작성·집필 전용 기능(전체 화면 집필, 장별 원고 편집, 소설용 템플릿/목표)은 이 앱의 공문서 후처리 목적과 멀어 제외한다. 이 설계에도 배경 상주 서비스나 독립 상주 EXE를 추가하지 않는다. 모든 자료 목록·검색·카드 화면은 사용자 요청 시 열고, 카드 데이터는 제목·상태·짧은 발췌만 메모리에 유지한다.

## 구조 결정 (2026-11-03 사용자 지시)

자료함과 로컬 검색은 **앱과 분리된 별도 프로세스**로 독립 작동하며, 최적·최소 자원을 위해 **Rust**로 만든다. 화면은 **Flutter**로 만든다. 앞 절의 Python 서비스(`docfit_core/library`, `docfit_app/library_service.py`)는 동작 규격과 시험 기준으로만 쓰고, 실제 색인·검색 엔진은 Rust로 옮긴다.

- **실행 파일**: 저장소 `klib/`의 Rust 크레이트가 `klib.exe`를 만든다. 몽땅클립보드 `kagent/`와 같은 방식(windows-sys, 네트워크 코드 없음, 릴리스 빌드 크기·메모리 최소화)으로 만들고 CI에서 함께 빌드해 `resources/klib.exe`로 넣는다.
- **수명**: 상주하지 않는다. 앱이나 자료함 화면이 요청할 때 시작하고, 색인·검색이 끝난 뒤 일정 시간(기본 60초) 요청이 없으면 스스로 종료한다. 앱 종료 상태에서 프로세스·CPU·메모리·핸들 0을 시험으로 확인한다. 같은 사용자 안에서는 한 개만 실행(뮤텍스, 시험용 격리 폴더 지원).
- **통신**: 사용자 SID가 붙은 로컬 named pipe, 한 줄 JSON 요청·응답(kagent `pipe.rs`와 같은 형식). 외부 네트워크 0회. 요청 종류: 자료함 만들기·수정·삭제, 폴더 추가·제거, 색인 시작·진행·취소, 파일명 검색, (4.0-B) 본문 검색, (4.0-C) 메모.
- **저장**: `%LOCALAPPDATA%\HwpAutoDocFit\library\library.db` SQLite(WAL). 본문 검색은 FTS5를 쓰기 위해 SQLite를 정적으로 묶는다(rusqlite `bundled`, CI의 MSVC로 빌드). 타임머신 DB와 섞지 않는다.
- **색인**: 지정 폴더만 증분 검사(경로·크기·수정 시각), 심볼릭 링크·정션 따라가지 않음, 네트워크·OneDrive 온디맨드 경로는 기본 제외, 한 파일 실패가 전체를 멈추지 않음. 원본은 읽기만 한다.
- **화면**: Flutter에 「자료함」 메뉴(기본 꺼짐 설정 뒤)를 추가한다. 화면은 Python 브리지를 거쳐 파이프로 `klib.exe`에 요청한다(웹뷰 안에서 직접 파이프를 열 수 없으므로). 브리지는 요청을 그대로 전달하고 경로 검증은 `klib.exe`가 다시 한다.
- **완료 기준(4.0-A)**: `cargo test` 통과, 10만 파일 메타데이터 색인·검색 실측(p95 300ms 이하 목표), 유휴 종료 확인, 화면 위젯 시험, 실제 앱에서 자료함 만들기→폴더 추가→검색→열기 판정.
