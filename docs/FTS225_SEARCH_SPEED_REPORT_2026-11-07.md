# FTS225 위계기반 본문검색 응답 속도 측정 보고 (2026-11-07)

## 결론
SQL 집계(GROUP BY) 방식은 **메모리는 약 75% 줄지만 응답시간은 줄지 않았다**(오히려 0~30% 느림).
카드 기준("효과가 숫자로 없으면 코드는 커밋하지 않고 측정만 보고")에 따라 **제품 코드는 커밋하지 않았다.**

## 시도한 변경
- `ContentSearchIndex.search`의 3~4단계(일치 문단 전체를 Python으로 가져와 집계)를 후보 문서 한정 SQL 집계로 교체:
  `WITH hits AS (MATCH + path IN json_each(후보)) SELECT path, SUM(검색어별 횟수), MIN(최상위 위계), MIN(bm25) GROUP BY path HAVING 모든 검색어>0`.
- 상위 N건 문서의 대표 문단(스니펫)만 한 번의 질의로 조회. 제외어 경로는 별도 질의 유지.
- near(~N) 연산자·비ASCII 대소문자 검색어(SQLite lower()가 ASCII만 접음)는 기존 Python 경로로 대체.
- 패치·측정 스크립트는 저장소 밖 `hwp-fts225-artifacts/`에 보관(커밋하지 않음).

## 측정 방법
임시 폴더의 합성 DB(사용자 실제 DB 미사용). 문서당 문단 20개, 위계 무작위, 한/글 COM 미사용. limit=100,
시간은 3회 중 최소(ms), 메모리는 tracemalloc 최대치. 맥(Python 3.14, SQLite 3.50.4) 측정이므로 Windows 절대값과 다를 수 있다.

관련 시험(content_search·service·related 110건)의 실패 목록도 전후 동일(맥 환경 기존 실패 6건, 새 실패 0).

## 원인 분석
- 시간의 바닥은 SQLite의 FTS 일치 문단 전체 스캔과 본문 읽기(MATCH만으로 약 20~25ms/3만 문단)이며,
  SQL 안의 lower·replace·instr 집계가 이를 Python 집계와 비슷한 비용(약 60ms)으로 되풀이한다.
- Python 전송·집계를 없애도 SQL 문자열 연산 비용이 상쇄하고, 후보 JSON 필터와 상위 N 대표 문단 재조회(약 16~20ms)가 더해진다.
- 첫 시도에서 문서별 재조회(MATCH 100회)는 1.6초로 급증했다(FTS 가상 테이블의 path는 색인이 없음) → 한 번의 IN 조회로 교체했으나 위 수치에 머문다.
