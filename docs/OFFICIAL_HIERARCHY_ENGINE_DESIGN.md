# 공문서 공통 위계 분석 엔진 설계

작성: 2026-11-04 · 개발 대상: v2.2.14 · 기준 정식 릴리스: v2.2.13

## 목표와 결정

공문서의 제목·개요·항목 위계를 한 번 일관되게 판정해 서식 분석과 위계기반 본문검색이 함께 사용한다. 위계 판정 코어는 Rust로 개발하고 화면은 Flutter로 제공한다. 기존 Python 문서 추출·한/글 COM 경로는 교체 전까지 입력 어댑터로만 남긴다. 판정 결과는 Flutter FFI를 통해 소비하며 Python 분석 구현을 새 기준으로 확장하지 않는다.

우선순위는 정확성을 유지하면서 문단 수에 선형으로 비례하는 처리 시간, 작은 추가 메모리, 오프라인 동작이다. 네트워크·LLM·상시 백그라운드 서비스는 사용하지 않는다.

## 입력과 출력

문서 추출기는 문서 순서대로 문단 레코드를 만든다. 각 레코드는 UTF-8 텍스트 범위, 표 셀 여부, 제목/개요 스타일 힌트, 글꼴 ID, 크기(정수 단위), 왼쪽/첫 줄 들여쓰기(HWP 단위), 선택적 문단 위 간격을 가진다. 텍스트는 하나의 UTF-8 버퍼에 모으고 레코드는 버퍼의 offset/length를 참조한다. FFI 경계에서 문단별 문자열을 복제하거나 JSON으로 직렬화하지 않는다.

Rust 코어 출력은 문단 순서와 같은 길이의 작은 고정 레코드 배열이다: 역할 enum, 신뢰도 등급, 표 셀/모호성 플래그, marker family ID, 부모 문단 인덱스(필요한 모드에서만). 전체 서식 분석은 이 배열에서 역할별 빈도·대표 들여쓰기·글꼴/크기·구조 경고를 반환한다. 검색 인덱스는 역할 enum을 위계 순위 정수로 저장하고, 본문 검색은 기존 정책대로 최고 위계 → 언급 횟수 → 최근 날짜 → BM25로 정렬한다.

## 위계 판정 규칙

1. 표 셀 문단은 `table_cell`로 고정한다.
2. 문서 형식이 제공한 명시적 제목/개요 스타일 또는 outline level을 우선한다. 출처 형식별 level을 공통 역할 enum으로 정규화한다.
3. 문두 번호·기호는 원문을 보존하면서 계열과 깊이만 판별한다. 날짜, 문서번호, 붙임/참고 블록, 문장 내부 기호는 목록 표식으로 오인하지 않는다. 단독 번호는 문서 내 연속성/계열 근거가 없으면 장·절로 승격하지 않는다.
4. 명시 서식이 없는 문단은 문서 안의 관측값으로 역할을 추정한다. 계열별 들여쓰기 중앙 대표값을 먼저 비교하고, 동률에서만 글꼴·크기 차이를 사용한다. 여백은 분류 근거가 아닌 진단 정보다.
5. ①·㉠처럼 여러 단계로 쓰이는 표식은 같은 문서에서 확인된 들여쓰기·글꼴·크기 서명에 맞춰 분류한다. 근거가 부족하면 `ambiguous`와 낮은 신뢰도를 반환하고, 임의 승격하지 않는다.
6. 문단 역할을 구조 스택에 연결한다. 더 높은 단계 문단이 나오면 해당 단계 이상의 열린 부모를 닫는다. 부연설명은 직전 유효 항목에 연결한다. 본문 검색에서는 문단의 역할만 필요하므로 부모 연결과 경고 계산을 생략할 수 있다.

공통 역할 enum은 `document_title`, `chapter`, `section`, `topic`, `square`, `circle`, `dash`, `asterisk`, `body`, `table_cell`, `ambiguous`로 고정한다. 구형 한글 문서의 1~6단계 서식 용어는 이 enum에 매핑하되, 검색 위계 순서는 현재 확정 정책과 일치시킨다.

## 최고속도·최소 리소스 알고리즘

**1단계: 1회 특징 추출.** 각 문단의 첫 유효 문자부터 짧은 문두 구간만 읽어 스타일 힌트, 표 여부, 표식 계열·번호 ordinal·깊이를 산출한다. Rust의 바이트 기반 ASCII 판정과 필요한 구간만 UTF-8 문자 디코딩을 사용한다. 정규식 객체·임시 문자열·문단별 map을 만들지 않는다. 문서 전체 통계를 위해 계열별 빈도, 연속 번호 전이, 들여쓰기·글꼴·크기 서명 카운터를 갱신한다. 카운터는 고정된 marker family/level 슬롯과 관측된 서식 서명만 저장한다.

**2단계: 역할 판정 및 구조 연결.** 입력과 추출된 compact feature를 순서대로 다시 순회한다. 문서 통계와 명시 스타일을 이용해 역할 enum을 기록하고, 고정 크기 위계 스택으로 부모를 연결한다. 검색 모드는 역할 순위만 반환하고 즉시 끝낸다. 서식 분석 모드만 구조 경고·대표 서식 통계를 함께 산출한다.

**3단계: 경고와 요약.** 문서의 선후 조건은 접미/접두 누적 플래그로 한 번씩 훑는다. 예를 들어 뒤에 본문이 있는지 역방향 누적 배열 또는 다음 유효 역할 인덱스로 확인하고, 앞선 상위 항목은 정방향 상태 하나로 판단한다. 문단마다 뒤쪽 전체를 다시 검색하지 않는다.

시간 복잡도는 `O(N + T)`(N=문단 수, T=문두 표식 판별에 읽은 총 글자 수)이며, 추가 공간은 compact 문단 특징과 출력 배열을 포함해 `O(N + K)`(K=고정 계열 수 + 관측 서식 서명 수)다. 원문 본문은 코어에서 복제하지 않는다. 검색 전용 모드는 부모·서식 variant·경고 생성을 건너뛰어 추가 메모리와 분기를 줄인다. 반복 검색은 색인된 역할 값을 재사용하므로 문서 위계 분석을 검색 요청마다 다시 실행하지 않는다.

## Rust·Flutter 연결

- 코어 crate는 표준 라이브러리 중심으로 작성하고 `unsafe`를 코어에서 금지한다. C ABI 경계만 별도 FFI 모듈로 격리한다.
- Flutter 화면은 `dart:ffi`로 Windows `cdylib`를 호출한다. API는 버전·구조체 크기를 포함하고 입력 텍스트 버퍼와 레코드 배열을 한 번에 전달한다. 출력은 호출자가 할당한 고정 배열에 기록해 Rust↔Dart 문자열 왕복과 allocator 교차 해제를 없앤다.
- 긴 문서는 Flutter UI 스레드에서 분석하지 않는다. 기존 백그라운드 작업/Isolate에서 호출하고 취소 토큰을 문단 배치 경계에서 확인한다. 검색 결과 표시는 Flutter가 역할 enum을 현지화한다.
- 기존 Python 문서 추출기는 단계적 이행 중 포맷 어댑터로 유지한다. 동일 레코드를 Rust 코어에 전달하고, 출력 역할만 HWPX 색인·서식 분석에 연결한다. 포맷별 추출 완료 후 Rust 분석 1회를 보장한다.
- PyInstaller 패키지에는 버전이 일치하는 Rust DLL을 포함한다. 누락·ABI 불일치 시 앱 시작을 막지 말고 명확한 진단을 내며 호환 모드로 전환한다. 최종 배포에서는 Rust 경로 사용 여부를 진단 정보로 확인한다.

## 검증과 성능 목표

먼저 현 Python 결과를 고정 골든 자료로 만들고, 동일 입력에서 Rust 역할 배열·부모 연결·경고·문서 유형을 비교한다. 알려진 공문서 양식, 연속·불연속 번호, 문두 날짜/문서번호, 표 셀, 붙임 영역, 원문자, 잘못된 들여쓰기, 빈 문단을 포함한다. 의미가 달라지는 예외는 골든을 임의로 갱신하지 않고 규칙과 샘플을 검토한다.

성능 게이트는 동일한 Windows 저사양 기준 장비에서 cold/warm을 분리해 측정한다. 초기 목표는 10,000문단 검색 분류 p95 50ms 이하, 50,000문단 전체 서식 분석 p95 500ms 이하, Rust 코어 추가 peak memory 8MiB 이하(입력 UTF-8 버퍼와 결과 배열 제외)다. 측정에는 10회 warm-up 및 30회 반복, 대표/최악 입력(기호 밀집, 긴 문단, 원문자 다수)을 포함한다. 목표 미달 시 먼저 FFI 복사, 할당 수, marker 판별 횟수를 계측하고 SIMD나 병렬 처리는 측정으로 이득이 확인될 때만 검토한다.

## 단계적 구현

1. Rust workspace와 고정 enum/구조체 API를 만들고 골든 시험으로 표식 파서·2단계 분류기를 구현한다.
2. Flutter Windows FFI 빌드·로딩·버전 검증을 연결하고 성능 계측 화면/로그를 개발 진단에 한정한다.
3. 서식 분석에서 Rust 결과를 shadow 비교한 뒤 Rust 결과를 채택한다.
4. 타임라인 본문 색인을 Rust 결과로 생성하고 계층 스키마 버전을 올려 증분 재색인한다. 검색 시에는 저장된 위계 rank를 재사용한다.
5. 골든 일치율, 성능 게이트, Windows 패키지 DLL 로딩 검증이 모두 통과하면 Python의 중복 위계 판정 경로를 제거한다.

## 최적 분석 방법(2026-11-04 확정, v2.2.15 개발)

원칙: 문단을 하나씩 따로 판정하지 않는다. **이 문서가 쓰는 번호 체계를 먼저 추정한 뒤, 모든 문단을 한꺼번에 가장 모순 없게 배치**한다. 위계 단계는 **최대 8단계**다.

### 1단계 — 표식 계열 목록 만들기(첫 단계)

- 각 문단 맨 앞 표식을 계열·순번·꾸밈으로 나눈다. 번호 계열(Ⅰ. 1. 가. (1) (가) ① ㉮ 등), 기호 계열(□ ㅇ - * 등).
- 날짜(2024. 3. 5.), 문서번호, 금액(1,000), 소수(1.5%), 문장 중간 기호는 표식에서 뺀다.
- 계열별 근거를 기록: 출현 수, 첫 위치, 들여쓰기 중앙값, 글자 크기·굵기, 순번이 1로 다시 시작한 지점.
- 결과: 이 문서의 계열 목록(최대 8개). 9개 이상이면 들여쓰기·글자 서명이 같은 계열을 같은 단계로 묶고 "같은 단계, 다른 기호" 진단을 낸다.

### 2단계 — 계열 순서 정하기

근거를 가중 투표로 합쳐 계열의 상하 순서(1~8위)를 정한다.
1. 끼임과 다시 세기: B 순번이 A가 나올 때마다 1로 돌아가면 A가 상위(가장 강한 근거).
2. 들여쓰기 중앙값이 작을수록 상위.
3. 글자 크기·굵기(동률일 때만).
4. 처음 나온 순서와 공문서 관례(Ⅰ > 1. > 가. > (1) > (가) > ① > ㉮, □ > ㅇ > - > *)는 근거가 부족할 때만 쓴다.

### 3단계 — 전체 문단 배치(최소 모순 경로)

문단을 순서대로 놓고 단계 배정마다 비용을 매긴다: 들여쓰기가 그 단계 대표값과 다름, 순번 끊김(1 다음 3), 상위 없이 하위 먼저, 2단계 순서와 어긋남. 비용 합이 최소인 배정을 동적 계획법으로 찾는다(단계 ≤ 8이므로 O(N·64)). ①·㉠처럼 여러 단계에 쓰이는 기호도 이 과정에서 맥락으로 결정된다.

### 4단계 — 표식 없는 문단

- 소제목: 짧고 명사로 끝나고 굵거나 크며 뒤에 하위 항목이 따라옴.
- 부연설명: 앞 항목보다 더 들여 쓰거나 ※·*로 시작 → 앞 항목에 연결.
- 나머지는 본문. 문서 머리(기관명·제목·수신·결재)와 붙임·참고 영역은 미리 나누어, 붙임 안 번호는 따로 센다.

### 출력과 신뢰도

역할 enum, 부모 문단, 신뢰도(최선과 차선 배정의 비용 차), 진단(번호 건너뜀, 단계 건너뜀, 같은 단계 다른 서식). 신뢰도가 낮으면 `ambiguous`로 두고 억지로 올리지 않는다.

### 검증

실제 공문서 50~100건 사본에 문단별 정답 위계를 붙여 골든으로 쓴다(원본 수정 금지). 지표: 문단 정확도, 부모 연결 정확도, 보류 비율. 기준선(현 Python 판정, v2.2.14 Rust 1단계)보다 정확도가 떨어지면 채택하지 않는다. 적용 순서: v2.2.15 1·2단계 shadow 비교 → 3·4단계 → 정확도 확인 뒤 색인·서식 통일 전환.
