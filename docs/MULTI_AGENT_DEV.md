# 멀티 에이전트 개발 운영 설계 (HWP AutoDocFit)

작성: 2026-11-03, PM(오케스트레이터) 에이전트. 대상: 이 저장소에서 여러 AI 에이전트가 분업할 때의 공통 규칙.
기본 규칙은 `HANDOVER.md`·`AGENTS.md`가 우선하며, 이 문서는 그 위에 **역할 분담과 작업 흐름**만 더한다.

---

## 1. 역할 구성

| 역할 | 맡는 일 | 산출물 | 쓰기 권한 |
|---|---|---|---|
| **PM(오케스트레이터)** | 요구사항 정리, 기능 명세·수락 기준, 작업 분배, 결과 병합, 커밋·푸시, 사용자 보고 | 스프린트 보드 `docs/agent_board/SPRINT_NN.md`, 최종 보고 | 저장소 전체(병합·커밋 담당은 PM 하나) |
| **설계자(아키텍트)** | 현행 코드 조사, 변경 범위·인터페이스(함수 서명·IPC 응답 형태)·위험 결정 | 보드의 "설계" 절(PM이 옮겨 적음) | 읽기 전용 |
| **개발자 — 코어/서비스(Python)** | `docfit_core/`·`docfit_app/` 구현과 단위 시험 | 코드 + `tests/test_*.py` | 보드에 배정된 파일만 |
| **개발자 — 화면(Flutter)** | `flutter_ui/lib/`·`flutter_ui/test/` 구현 | 코드 + 위젯 시험 | 보드에 배정된 파일만 |
| **리뷰어·테스터** | 변경 검토(정확성·규칙 위반), 시험 실행, 경계값 시험 추가 제안, 결함 반려 | 보드의 "검토" 절(결함 목록·판정) | 읽기 + 시험 실행(코드 수정은 하지 않음) |

원칙: **같은 파일을 두 개발자에게 동시에 배정하지 않는다.** 병렬 작업은 파일 소유권으로 충돌을 막는다.

## 2. 작업 흐름(반복 루프)

```
계획(PM) → 설계(아키텍트) → 작업 분배(PM) → 구현(개발자 병렬) → 검토·시험(리뷰어)
   ↑                                                                    │
   └────────────── 결함 반려 → 수정(해당 개발자) → 재검토 ←───────────────┘
                                   │ 통과
                                   ▼
                    병합·전체 시험·커밋·푸시(PM) → 보고(PM)
```

1. **계획**: PM이 `TODO.md`·사용자 요청에서 이번 스프린트 범위를 정하고 보드에 목표·수락 기준을 쓴다.
2. **설계**: 아키텍트가 코드를 조사해 변경 지점, 인터페이스, 하위 호환, 위험을 정한다. 결정이 사용자 몫이면 PM이 질문으로 올린다.
3. **분배**: PM이 작업을 파일 소유권 단위로 나눠 개발자에게 배정한다(작업 ID `S01-T1` 형식).
4. **구현**: 개발자는 배정 파일만 고치고, 자기 영역 시험을 통과시킨 뒤 변경 요약을 PM에게 돌려준다. 커밋은 하지 않는다.
5. **검토·시험**: 리뷰어가 diff 전체를 읽고 시험을 실행한다. 결함은 `심각도 / 파일:줄 / 재현 / 기대 동작`으로 적는다.
6. **수정**: 결함이 있으면 PM이 해당 개발자에게 반려하고 4~5를 반복한다(최대 2회, 넘으면 사용자에게 보고).
7. **병합**: PM이 전체 시험(`python -m unittest discover -s tests`)을 돌리고 `alpha`에 커밋·푸시한 뒤 보드를 닫는다.

## 3. 공통 작업 공간

- **Git 저장소**: 모든 결과물의 단일 원천. 작업 브랜치는 `alpha`(HANDOVER 5절). 개발자 에이전트는 같은 작업 트리에서 배정 파일만 수정한다.
- **스프린트 보드** `docs/agent_board/SPRINT_NN.md`: 목표·수락 기준·설계·작업 목록(담당·상태)·검토 결과·남은 위험. 상태 값: `대기` / `진행` / `검토` / `반려` / `완료`.
- **TODO.md**: 사용자 요청 원천. 스프린트가 끝나면 완료 항목을 근거(파일·시험)와 함께 갱신한다.

## 4. 이 환경에서의 검증 한계

- 클라우드 리눅스 컨테이너에서는 **한/글 COM·WebView2·Windows 전용 동작을 시험할 수 없다**. 순수 파이썬 코어·서비스 시험은 여기서 돌리고, 실기 확인이 필요한 항목은 보드의 "실기 확인 필요"에 남긴다.
- Flutter SDK가 없는 환경에서는 Dart 코드를 정적으로 검토만 하고, `flutter test`는 Windows/CI에서 확인할 항목으로 남긴다.
- 사용자 문서 원본은 다루지 않는다. 시험은 임시 폴더의 합성 데이터로만 한다.

## 5. 에이전트에게 주는 지시 양식

각 에이전트 지시에는 다음을 반드시 넣는다: ① 역할 ② 작업 ID와 목표 ③ 수정 가능한 파일 목록 ④ 지켜야 할 규칙(defusedxml, CRLF, 한국어 주석, 커밋 금지) ⑤ 완료 조건(통과해야 할 시험) ⑥ 돌려줄 보고 형식.
