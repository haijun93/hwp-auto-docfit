# PAX HWPX 편집 프로젝트 비교·벤치마킹 조사

> 후속 재평가: [Beta 12 코드 리뷰·벤치마킹 재평가](Beta12_코드리뷰_벤치마킹_재평가_2026-10-09.md). 아래는 이전 알파 기준 조사다. 최신 베타의 구현 상태·쪽 정책·우선순위는 후속 보고서를 우선 참고한다.

조사일: 2026-10-09(KST). 비교 기준: 현재 작업 폴더 `alpha`, HEAD `8ab28c3`, 앱 표기 `1.73 Alpha 1` 및 미커밋 작업본. 조사 중 기존 수정 파일 `hwp-auto-docfit.py`, `scripts/regression_pc.py`는 변경하지 않았다.

## 1. 결론

- 현재 앱의 강점은 **완성된 공문서의 자간·내어쓰기·표 묶음·쪽 구성을 한/글 실측으로 후처리하는 것**이다. 외부 프로젝트의 범용 편집 기능 수와 직접 비교하면 이 강점이 가려진다.
- 우선 벤치마킹 대상은 **kordoc(패치·검증·공개 측정), hwpx-skill(치환 사전검사·실패 결과 차단), auto-hwp(편집 명령·변경 미리보기), Rekian(서식/내용 분리), 내편공문(제안 선택·고유명 보호)**이다.
- 현재 코드에도 XML 일괄 서식, 최소 변경 패치, 원문 위치 맵, 다층 검증, kordoc 연동이 있다. 이를 새로 만드는 대신 **같은 실행 경로에서 결과·미적용 사유·검증 상태를 일관되게 보여주는 작업**이 우선이다.
- 감마의 한컴 비의존 경로에는 rhwp·auto-hwp를 검토할 가치가 있다. 알파의 실측 조판을 바로 대체할 근거는 이번 조사에서 확보하지 못했다.
- 메일 머지·문서 병합·이미지 최적화는 실무 확장 후보다. 현재 쪽 구성 회귀 해결과 XML 경로 확장보다 앞세우지는 않는 것을 권한다.

## 2. 검색 범위와 증거 수준

[PAX](https://hollobit.github.io/PAX/) 화면은 동적 데이터 로딩 때문에 웹 읽기에서 사례가 표시되지 않았다. 따라서 [사이트 배포 데이터](https://raw.githubusercontent.com/hollobit/PAX/main/site/data/cases.json)의 522건 전체 JSON을 검색했다. `hwpx|hwp|한글.*편집|한/글|kordoc|rhwp|범피스|범정부오피스`에 해당하는 **47개 사례**를 추렸다. 중간 검색에서 안내한 43건은 검색어 확대 전 결과다.

후보마다 제목·설명·태그·링크를 검토하고, 핵심 대상은 개발자 README 또는 공식 제품 페이지를 추가로 확인했다. GitLab은 웹 읽기에서 README가 생략되어 공개 API로 프로젝트 기본 브랜치와 `README.md`를 읽었다. 상세 목록은 아래 전수 후보 부록에 남겼다.

이 문서의 분류:

- **직접 편집**: 기존 HWPX를 읽고 내용·서식·구조를 바꾸거나 수정 저장을 지원한다고 원문에서 확인.
- **생성·양식·가공**: 새 HWPX 작성, 양식 채우기, 병합, 이미지 변경. 범용 기존 문서 편집과 구별.
- **지원 확인 필요**: HWP 편집은 소개되지만 HWPX 저장·보존 범위를 명확히 확인하지 못함.
- **인접 기능**: 추출·검색·검수·PDF 출력 등으로 기존 HWPX 변경이 확인되지 않음.

이는 **PAX 수록 사례를 대상으로 한 전수 후보 검색**이다. 설명에 HWP/HWPX 관련 표현이 전혀 없는 숨은 기능까지 모두 발견했다는 의미는 아니다. PAX 요약과 개발자 성능 주장은 독립 실험 결과가 아니다. 이번에는 외부 앱 설치, 사용자 문서 처리, 성능 측정, 네트워크 0바이트 검증을 하지 않았다.

## 3. 현재 코드의 실제 강점과 한계

| 항목 | 현재 구현 근거 | 비교에서의 의미 |
|---|---|---|
| 공문서 후처리 | 앱 본체의 자간·내어쓰기·표 묶음·쪽 맞춤·저장결과 검수 | 범용 편집기보다 업무 규칙이 구체적. 한/글 조판으로 줄·쪽을 확인할 수 있음 |
| XML 선적용 | `docfit_core/batch_format.py`의 `apply_batch`, `StylePool`, `ParagraphStyle` | COM 반복 호출을 줄이는 경로가 이미 있음. 단순 문단 중심이며 복잡한 컨트롤·중복 문장은 기존 경로로 넘김 |
| 서식 학습 | `style_inventory.py`, `format_elements.py`, `table_style.py` | 기관별 사용자 예시에서 역할별 대표값을 학습. 큰 문서·혼합 서식에서 대표값의 한계가 있음 |
| 최소 변경 | `fidelity/package.py`, `source_map.py`, `patch_hwpx.py` | 미수정 압축 항목 보존, 원본 해시·대상·기존 글 확인. 공문서 후처리 전체에 자동 적용되는 보증은 아님 |
| 패치 한계 | `replace_text`, `set_paragraph_text`만 지원 | 서로 다른 run을 가로지르는 치환은 거부. 문단 전체 교체는 첫 run 서식 적용, 특수 텍스트 요소가 섞이면 거부 |
| 다층 검증 | `fidelity/verify.py`의 `verify_patch` | 패키지·원문 보존·구조/내용 비교. `native`를 넘기지 않으면 한/글 열기는 `not_run`; 화면 일치 보증과 구별해야 함 |
| 외부 엔진 연동 | `kordoc_bridge.py`의 파싱·양식 채움·패치·생성·렌더 | 해당 기능을 전부 신규 개발할 필요 없음. 현재 `kordoc@^4`, `npx -y` 실행이라 재현성과 폐쇄망 설치 정책 보완 필요 |
| 실행 환경 | Windows·한/글 2020 COM, WebView2/Tk·Flutter UI | 실제 한/글 결과 확인에 유리. OS·설치·COM 상태 의존, 배포·테스트 환경 제약 |
| 유지보수 | 앱 본체에 COM·파이프라인·GUI가 함께 존재 | 엔진/명령/UI를 분리한 외부 구조를 참고할 가치가 큼 |

특히 kordoc 브리지는 Node 18 이상으로 안내하지만 현재 upstream README는 Node 20 이상을 요구한다. 패치 부분 적용의 반환 코드 2도 허용한다. **버전 고정·실행 환경 안내 정합성·부분 적용 판정의 사용자 표시**를 작은 개선 과제로 삼을 수 있다. 이 조사에서는 코드를 수정하지 않았다.

## 7. 동일 문서 비교 시험 설계

1. 사용자 원본 대신 임시 사본 또는 개인정보 없는 공개 양식을 사용한다. 간단 보고서, 혼합 강조 문단, 병합/중첩 표, 머리말·꼬리말·쪽 번호, 그림/도형, 다중 구역, 표를 포함한 붙임을 나눈다.
2. 기존 문서 편집 시험은 동일 파일에서 단순 글 치환·셀 값 치환·구간 서식·문단 서식·표 구조 변경을 따로 시행한다. 생성기는 생성 시험으로 분리한다.
3. 정확한 엔진 버전과 글꼴·OS·한/글 버전, 실행 설정을 기록한다. 각 작업의 열기/변경/저장/검수 시간과 메모리 사용을 구분한다. 시간 비교는 반복 측정의 중앙값과 실패율을 함께 제시한다.
4. 패키지/참조 유효성, 원문 내용, 병합 셀 포함 표 구조, 미수정 개체·서식, 한/글 열기, 쪽 수와 보고서/붙임별 쪽 범위, 시각 차이를 독립 판정한다.
5. 의도한 변경으로 생긴 줄/쪽 이동과 의도하지 않은 이동을 구분한다. 페이지 그림 비교는 글꼴·렌더 버전을 고정한다. 조판 캐시가 오래되었을 가능성 때문에 저장된 `lineseg`만을 정답으로 쓰지 않는다.
6. 알파 합격 기준은 기존의 쪽 구성 동일·본문 보존 원칙을 유지한다. 감마에서는 화면 일치 미확인·미지원 개체를 별도 상태로 노출한다.

예상 속도 개선률이나 외부 도구 대비 우위 비율은 실험 전 수치화하지 않는다. 현재 앱의 공개 등록 설명보다 실제 알파 코드의 범위가 넓으므로, PAX 소개만을 기준으로 기능 부족을 판단해서도 안 된다.

## 8. 조사에서 제외한 인접 분야

검색·RAG·규정 MCP·문서 리소스 추출·표→Excel·HWPX→HTML·PDF 마스킹·일괄 인쇄·홍보물 생성은 HWPX를 읽거나 다른 형식으로 내보내는 사례다. 이들에서 기존 HWPX 편집 기능을 확인하지 못했으므로 직접 경쟁 도구로 집계하지 않았다. 검수 도구는 기존 HWPX 수정 저장이 확인된 내편공문만 직접 편집 표에 올렸다.
