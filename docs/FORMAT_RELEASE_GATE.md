# 제목·항목기호·내어쓰기 서식 릴리즈 게이트

제목, 문두 항목기호, 본문 내어쓰기는 핵심 기능이다. 이 검수는 기능·테스트 개수·빌드 성공 여부만으로 대체하지 않는다. 필수 자동검사 또는 한/글 화면 검수가 하나라도 실패하거나 실행되지 않으면 릴리즈를 중단한다.

## 보장하는 검사

1. 처리 경로에서는 문단 모양 복사, 계층별 서식, 간격, 기호 글자모양을 적용한 다음 내어쓰기 쌍(`LeftMargin`, `Indentation`)을 마지막에 확정한다. 음수 내어쓰기만 남아 첫 줄이 왼쪽으로 밀리는 저장 결과를 방지한다.
2. `scripts/format_fidelity_pc.py`는 한 줄짜리 문단이라도 항목기호·번호 문단의 `intent`와 `left`를 비교한다. 이를 “문단 하나에만 준 수동 예외”로 빼지 않는다.
3. `docfit_core.release_format_audit.inspect_hanging_indent()`는 저장된 HWPX의 모든 탐지 항목기호 문단을 검사한다. 문단 수 0, 참조 누락, 들여쓰기 누락, 음수 들여쓰기와 보정 왼쪽 여백의 불일치, `left + intent < 0`은 실패다.
4. 최상위 `ㅁ`/`□` 항목 제목은 내어쓰기 예외다. 저장 결과에서 `LeftMargin=0`, `Indentation=0`이어야 하며, 음수 첫줄 들여쓰기가 남아 있으면 실패다. `○○과장` 같은 연락처 장식은 항목기호로 오인하지 않는다.
5. 최종 검사 범위에는 한 칸 표로 만든 제목·개요의 본문형 문장도 포함한다. 다중 셀 표 제외 설정은 이 영역에 적용하지 않으며, 사용자 장식표 보호는 유지한다.
6. `scripts/audit_saved_result.py`는 최종 저장 파일을 별도 한/글 COM 인스턴스로 읽고 검사하며 입력 파일 SHA-256이 유지됐는지 확인한다. 구조 검사가 실패하면 종료 코드도 실패다.
7. `scripts/release_format_regression.py`는 기준 입력을 사본으로 처리하고 100점 기준 회귀시험, 저장 결과 COM/구조 감사, 입력 원본 해시 보존을 묶어 실행한다. 한/글 COM이 없는 환경에서는 통과를 가장하지 않고 실패한다.

## 표준 실행 절차 (Windows + 한/글 COM PC)

아래 기준 문서를 반드시 포함한다. 경로에 있는 원본은 읽기만 하며, 결과와 로그는 별도 증거 폴더에 저장한다.

```powershell
.\.venv\Scripts\python.exe scripts\release_format_regression.py `
  "C:\HWP_AUTODOCFIT\테스트예시\보고서 예시 파일(한번에 적용).txt" `
  "$env:USERPROFILE\OneDrive\바탕 화면\111\test\내어쓰기 테스트.txt" `
  --out-dir "C:\HWP_AUTODOCFIT\release-evidence\format-gate"
```

통과하면 `release_gate.json`, `regression.json`, `results\`, `audits\`, `logs\`를 검수 증거로 함께 보관한다. 기존 결과물 옆에 이미 있던 JSON은 새 검사 증거로 인정하지 않는다.

## 화면 캡처 대조 검수 (필수)

자동 XML·COM 검사는 렌더링 동일성을 보증하지 않는다. 따라서 원본과 결과물을 한/글에서 같은 조건으로 열고 **모든 페이지를 화면 캡처해 짝별로 대조**한다. 이 검수는 자동검사 결과로 대체할 수 없다.

1. 시험 입력은 원본을 변경하지 않고 사본으로 열며, 결과물은 이번 실행에서 생성된 파일만 사용한다. 같은 PC·한/글 버전·화면 해상도·배율·창 크기·글꼴·용지/여백 설정을 유지한다.
2. 원본과 결과물 각각 첫 페이지부터 마지막 페이지까지 한 페이지 전체가 보이도록 캡처한다. 페이지가 화면보다 크면 같은 배율로 상단/하단을 나누어 캡처하고 같은 구간끼리 대응시킨다. 스크롤 위치와 페이지 경계를 맞추며, 메뉴/대화상자가 본문을 가리지 않게 한다.
3. 증거 폴더에 `visual-review/original/page-001.png` 및 `visual-review/result/page-001.png`처럼 페이지 번호가 같은 파일명으로 보존한다. 캡처를 자르거나 리사이즈·보정하지 않는다. 비교 편의를 위해 나란히 배치하거나 반투명 오버레이를 추가로 만들 수 있지만, 원본 캡처는 그대로 보존한다.
4. 각 페이지 쌍을 확대해 제목·개요, `□`/`ㅁ` 최상위 항목의 무내어쓰기, 하위 항목의 기호/본문 정렬, 글꼴·크기·굵기, 표와 쪽 경계, 줄바꿈·페이지 나눔을 확인한다. 결과를 저장·닫기·다시 열고도 같은 모양인지 캡처해 확인한다.
5. `visual-review/visual_review.json`에 검수자, 일시, OS/한글 버전, 해상도/배율, 페이지별 캡처 파일, 페이지별 판정과 차이를 기록한다. 원본·결과의 캡처 짝이 빠졌거나 의미 있는 차이가 하나라도 있으면 실패로 판정하고 릴리즈를 중단한다. “동일”은 이 기준 문서에 열거한 항목에서 시각적 차이가 없음을 사람이 확인했다는 뜻이다.

## 오류·사이드 이펙트 발생 단계 특정 절차

이 절차의 목적은 단순한 결과 확인이 아니라 **오류가 최초로 나타난 단계와 불필요한 시간 소요가 발생하는 단계를 분리해 찾는 것**이다.

1. 기준 실행의 전체 로그에서 `[처리 시간 단계별]` 순서를 확인한다. 각 단계의 실행 순서·개별 소요시간과 반복 횟수를 기록하고, 같은 입력·설정의 재실행에서 값이 재현되는지 확인한다. 최장 단계는 비효율 후보로 올리되, 느리다는 이유만으로 오류 원인이라고 단정하지 않는다.
2. 오류가 보이면 원본 사본과 설정을 고정하고, 처리 절차를 순서대로 진행하면서 각 처리 단계 직전/직후의 문서 화면을 캡처한다. 현재 실행에서 내부 단계 화면을 직접 멈춰 캡처할 수 없으면, 앱의 세부 작업 선택으로 동일 원본 사본에 **앞 단계까지 누적 적용한 실행**을 단계별로 반복해 각 단계 출력 HWPX를 만든다. 매 실행 결과를 열어 같은 페이지·같은 배율로 캡처한다.
3. `visual_review.json`의 `checkpoints`에는 기준선 및 제목·개요, 항목기호·내어쓰기, 자간·공백·표/컨트롤 후속 작업, 쪽 맞춤, 저장 후 재열기 단계의 전후 캡처를 기록한다. 추가 세부 단계가 로그에 나타나면 해당 단계도 체크포인트로 추가한다. 단계 누적 출력이 이전 단계 화면과 처음 달라지는 지점이 최초 회귀 후보이다.
4. 후보를 확정하기 위해 같은 기준 사본에서 후보 단계만 끈 대조 실행과 켠 실행을 각각 수행한다. 화면 차이와 저장 결과 구조감사에서 오류가 켠 실행에서만 재현되고, 끈 실행에서 사라질 때 해당 단계의 인과 근거로 기록한다. 단독으로 재현되지 않으면 후보 단계 조합을 추가로 비교해 상호작용을 확인한다.
5. 단계별 실행시간은 `[처리 시간 단계별]`에서 비교한다. 기준 대비 반복 초과, 같은 변경의 중복 적용, 결과 차이 없는 고비용 단계는 비효율 후보로 기록한다. 성능 개선으로 오류를 숨기지 않도록 각 실행의 서식·쪽 배치 검수 결과도 함께 비교한다.
6. 결과표에는 `단계명 / 직전·직후 캡처 / 최초 차이 / 켬·끔 대조 / 구조감사 / 소요시간 / 원인 확정 여부`를 적는다. 캡처가 없는 단계, 설정이 달라진 실행, 입력 해시가 다른 실행은 원인 판정 근거로 인정하지 않는다.

템플릿 생성:

```powershell
New-Item -ItemType Directory -Force "<증거폴더>\visual-review\original", "<증거폴더>\visual-review\result" | Out-Null
```

캡처 경로와 페이지·체크포인트별 사람 판정을 `visual_review.json`에 기록한 뒤 다음 검증기를 실행한다. 검증기는 원본·결과 이미지가 모두 존재하는지, 유효한 PNG인지, 해상도와 이미지 쌍이 대응되는지, 필수 단계 체크포인트·검수자·환경·판정이 빠지지 않았는지 검사하고 SHA-256 증거를 만든다. 입력 문서 전체가 검수 목록에 포함되지 않으면 실패한다.

회귀 실행이 생성한 `visual_review.json`을 유지하면서 `reviewer`, `reviewed_at`, `environment`를 채우고, 각 문서의 모든 페이지 쌍과 필수 체크포인트 전후 캡처를 채운다. 항목 형식은 다음과 같다.

```json
{"page":1,"original_png":"original/page-001.png","result_png":"result/page-001.png","decision":"pass","notes":"일치"}
{"id":"marker_indent","label":"항목기호·내어쓰기 처리 뒤","before_png":"checkpoints/marker_indent-before.png","after_png":"checkpoints/marker_indent-after.png","decision":"pass","notes":"□ 제목은 0/0, 하위 기호 본문 시작점 정렬 확인"}
```

모든 페이지·체크포인트의 사람 판정을 완료한 후 검증한다. 통과 시 검증기가 `visual_review_verified.json`을 생성하고 `release_gate.json`을 릴리즈 준비 상태로 바꾼다.

```powershell
.\.venv\Scripts\python.exe scripts\validate_visual_review.py "<증거폴더>\visual-review"
```

검증기는 파일 짝·기록 완전성을 확인할 뿐 이미지가 실제로 같은지 판정하지 않는다. 검수자가 모든 페이지를 직접 비교하고 각 쌍에 `decision: pass`와 관찰 결과를 기록해야 한다. 원본 캡처와 결과 캡처의 페이지 수는 동일해야 하며, 의도된 페이지 구성 변경이 승인되지 않은 한 페이지 수·페이지 경계가 다르면 실패다. TXT 입력처럼 원본에 페이지 서식이 없는 경우에는 “원본과 동일”을 주장하지 않고, 승인된 서식 기준/참조 화면과 결과를 대조한다.


## 판정 및 이력

릴리즈 후보 SHA, 소스 커밋, 앱 버전, Windows/한글 버전, 입력·출력 SHA-256, 실행 명령, 자동검사 JSON, 원본·결과 페이지별 캡처, `visual_review.json`을 함께 기록한다. 자동검사 통과는 화면 캡처 대조가 끝나기 전까지 릴리즈 승인이 아니다. 검사 상태가 `fail`, `error`, `not_run`, `pending`이거나 캡처/수동 검수가 빠졌으면 다운로드/릴리즈를 허용하지 않는다. 수정 후에는 같은 원본 사본으로 자동검사와 전체 페이지 검수를 처음부터 다시 수행한다.

이 게이트는 발견한 결함 유형을 막기 위한 회귀 방지 장치이며, 알려지지 않은 렌더링 결함이 앞으로 절대로 발생하지 않는다는 수학적 보증은 아니다. 그래서 정량 자동검사와 한/글 실제 화면 대조를 모두 필수로 둔다.
