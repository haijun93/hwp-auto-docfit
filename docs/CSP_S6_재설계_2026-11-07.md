# S6 Flutter 화면 CSP 재설계 (2026-11-07, 브랜치 feature/csp2)

범위: 정적 조사만 했다. 실행 시험은 Windows PC(WebView2)가 필요해 하지 못했다. "미확인" 항목은 아래에 따로 적었다.

## 1. 조사 결과

| 질문 | 결론 | 근거 |
|---|---|---|
| pywebview 주입이 CSP에 막히는가 | **막힌다(`'unsafe-eval'` 없으면).** | pywebview 6.2.1 `webview/js/api.js:75`가 노출한 API 함수마다 `new Function(params, body)`로 `window.pywebview.api.*`를 만든다. `script-src`에 `'unsafe-eval'`이 없으면 이 호출이 `EvalError`로 실패해 `get_state` 등이 생기지 않는다. 앱 전체가 먹통이 된다. |
| WebView2 `ExecuteScript`는 CSP 영향이 없는가 | **스크립트 본문 자체는 영향이 없지만, 그 안의 `new Function`·`eval`은 페이지 CSP를 받는다.** | `platforms/edgechromium.py:154`는 `ExecuteScriptAsync(script)`로 실행한다. 이 경로는 `<script>` 태그가 아니라 인라인 스크립트 제한을 받지 않는다. 하지만 위 `api.js`가 그 안에서 `new Function`을 호출한다. (CDP `Runtime.evaluate`와 같은 계열이라는 점은 Chromium 동작 기준이며 WebView2 실측은 미확인.) |
| Playwright 확인 스크립트를 문자열 평가 없이 바꿀 수 있는가 | **Python Playwright에서는 `wait_for_function`을 eval 없이 쓸 수 없다.** 대신 CDP `Runtime.evaluate`를 직접 호출하는 방식으로 우회할 수 있다. | Python API는 함수를 문자열로만 넘기고, 페이지 안에서 평가한다. `scripts/smoke_webview_content.py`의 `wait_for_function`(2곳)·`evaluate`(1곳)가 이에 해당한다. |
| `Injecting <script> tag. Using callback.` | 설치한 pywebview 6.2.1 소스에서는 이 문구를 찾지 못했다. | 다른 버전이나 앱 로그의 문구일 수 있다. 확인 필요. |

핵심: pywebview가 `'unsafe-eval'`을 요구하므로 (a) "eval 없이 고치고 `'wasm-unsafe-eval'`만 허용"은 **실현 불가**하다. 확인 스크립트만 고쳐서는 해결되지 않는다.

## 2. 제안 (b): 최소 범위 정책

v2.2.30 정책에서 `script-src`에 `'unsafe-eval'` 하나만 더한다. 나머지는 그대로다.

```
default-src 'self';
script-src 'self' 'wasm-unsafe-eval' 'unsafe-eval';
style-src 'self' 'unsafe-inline';
img-src 'self' data: blob:;
font-src 'self' data:;
connect-src 'self' data: blob:;
worker-src 'self' blob:;
object-src 'none';
base-uri 'self';
form-action 'none'
```

- 지키는 것: 인라인 `<script>`·이벤트 핸들러 속성, 외부 도메인 스크립트·이미지·연결, 플러그인(`object-src`), `<base>` 변조, 폼 전송. 로컬 문서 내용이 HTML로 주입되는 경우의 피해를 줄인다.
- 못 지키는 것: `eval`·`new Function` 기반 코드 실행. `'unsafe-eval'`이 있으므로 이 방어는 없다. 이 앱은 pywebview 구조상 피할 수 없다.
- 효과가 작은 이유를 숨기지 않는다. 이 정책의 가치는 "외부 로드 차단"에 있고 "스크립트 실행 차단"에는 없다.

## 3. 적용 전 필요한 작업 (Windows 필요)

1. `flutter_ui/web/index.html`에 위 meta를 넣는다. 인라인 스크립트는 이미 `docfit_bridge.js`로 분리되어 있다.
2. `scripts/smoke_webview_content.py`의 문자열 평가가 CSP에서 막히는지 CI에서 확인한다. 막히면 `page.context.new_cdp_session(page)`로 `Runtime.evaluate`(`returnByValue`, `awaitPromise`)를 호출하고 Python 쪽 반복문으로 대기하도록 바꾼다. 이 경우 `'unsafe-eval'` 없이도 검사는 되지만 앱은 위 2절 정책이 필요하다.
3. 빌드된 EXE로 화면이 뜨는지, 콘솔의 `Content Security Policy` 위반 로그가 0건인지 `result['console']`로 확인한다. Flutter CanvasKit(`wasm-unsafe-eval`)·웹 워커(`blob:`)·글꼴이 막히지 않는지 함께 본다.
4. `tests/test_zip_safety_csp.py`의 보류를 풀 때 `'unsafe-eval'` 부재 검사를 "있어야 함(pywebview 요구, 이유 주석)"으로 바꾼다.

이번 변경에서는 앱 동작을 바꾸지 않았다(`index.html` 무변경). 실제 확인 없이 다시 넣으면 v2.2.30처럼 CI가 깨질 수 있어서다.
